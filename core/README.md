# SmartESP core

Ядро домашнего голосового ассистента (сервер на Mac): принимает речь с
колонок ESP32, распознаёт, отвечает через локальную модель и озвучивает.
Дизайн: `../docs/superpowers/specs/2026-11-18-core-design.md`.

Для повседневной работы ядро запускает Mac-приложение — см. `../app/README.md`.

## Установка

Нужны `uv` и Python 3.12 (`uv python install 3.12`).

```
cd core
uv sync
```

`mlx-whisper` тянет `torch` — установка долгая, это нормально.

Для голосовых сообщений через API (Telegram) и файлов на колонке нужен `ffmpeg`:
`brew install ffmpeg`. Без него всё остальное работает, а `POST /api/v1/ask/voice` и
`POST /api/v1/devices/{id}/play` отвечают 503.

## Проверка

```
uv run pytest
uv run ruff check && uv run ruff format --check
uv run pyright
```

## Голос

Голоса скачиваются сами: при старте и при выборе нового голоса (отдельных
скриптов нет). Голос по умолчанию — Silero «xenia».

| Вид | Голоса | Размер | Скорость на фразу | Лицензия |
|---|---|---|---|---|
| `silero` | xenia, baya, kseniya | ~145 МБ | ~0,03 с | CC BY-NC-SA: **только некоммерческое использование** |
| `vosk` | female_0, female_1, female_2 | ~900 МБ | ~0,46 с | Apache 2.0 |
| `piper` | ru_RU-irina-medium (и другие `.onnx` в `voices/`) | ~63 МБ | ~0,07 с | MIT |

Голос выбирается в приложении или в `config.yaml`:

```yaml
tts: {kind: vosk, voice: female_1}
```

Голос открывается в фоне при старте, ядро не ждёт скачивания. Пока нужный голос
качается (или нет интернета), ядро говорит уже скачанным голосом — выбранным, если
он есть, иначе любым другим — и пишет об этом в журнал. Скачивание повторяется
через 30 с, 2 мин, 5 мин, дальше каждые 5 мин; когда голос готов, ядро
переключается на него само. Если скачанных голосов нет совсем, ядро всё равно
стартует, но колонки получают сигнал ошибки, пока голос не появится.

## Запуск

```
cd core
uv run python -m smartesp
```

`python -m smartesp` запускают из `core/`: это виртуальный проект uv (пакет не
установлен в окружение), и из другой папки модуль `smartesp` не найдётся.

Флаги:
- `--parent-watch` — остановиться, когда родитель закроет stdin (так ядро
  запускает приложение, чтобы ядро не осталось без хозяина);
- `--openapi PATH` — записать схему OpenAPI в файл и выйти (сервер не
  стартует, ничего не греется).

Перед запуском должна работать Ollama (`ollama serve` или приложение) с моделью
из `config.yaml` (`ollama pull <модель>`). Если Ollama недоступна, ядро всё равно
стартует (в журнале «Ollama недоступна: …»), но на вопросы колонка будет
отвечать сигналом ошибки.

Первый запуск:
- создаётся `~/SmartEsp/config.yaml` — пустой, с подсказками (см. «Настройки»);
- mlx-whisper скачивает модель распознавания (~1,6 ГБ) в кеш Hugging Face —
  первый старт долгий, дальше модель берётся из кеша.

При старте ядро прогревает модели (в журнале «Исполнитель прогрет…»,
«STT прогрет…»), затем слушает колонки на `ws://<mac>:8765/device`
(адрес и порт — `server` в `config.yaml`). Сервер поднимается сразу, прогрев
идёт в фоне: пока состояние `warming`, колонка на фразу получает сигнал ошибки.
Остановка — Ctrl+C.

## Настройки

В `~/SmartEsp/config.yaml` лежит только то, что вы поменяли сами; всё остальное
ядро берёт из своих значений по умолчанию, поэтому новые возможности появляются
сами, без правки файла. Все значения по умолчанию — рядом, в
`config.defaults.yaml` (только для справки, ядро перезаписывает его при старте):
чтобы что-то поменять, перенесите ключ оттуда в `config.yaml` и перезапустите ядро
(или меняйте настройки через API — см. «Приложение и API»).

Файл прежнего формата (все настройки целиком) ядро при первом старте переводит
само: оставляет только ваши изменения, старый файл сохраняет как `config.yaml.bak`.

Неизвестный ключ в `config.yaml` (опечатка вроде `histroy:` или ключ из более
новой версии) ядру не мешает: оно его не использует, пишет предупреждение в
журнал и не показывает в `overridden`; при первой записи настроек через API такой
ключ из файла пропадает. Неизвестный ключ в самой правке `PATCH /config` — 422.

### Что меняется на лету

Настройки, изменённые через `PATCH /api/v1/config`, ядро применяет без перезапуска
и сразу записывает в `config.yaml`:

- **на лету:** `devices`, `tts`, `executors`, `stages`, `history`, `speech`, `connectors`;
- **требуют перезапуска:** `server`, `stt`, `arbitration` — такая правка
  записывается, ответ получает `status: restart_required`, а `GET /status`
  показывает `restart_required: true`, пока ядро не перезапустят.

Смена голоса или модели при звучащем ответе ничего не обрывает: идущий ход
договаривает старыми частями, следующий берёт новые, старая модель выгружается из
Ollama после конца хода. Новая модель сначала прогревается (до 120 с), и только
потом подменяет старую. Несколько быстрых правок применяются по очереди, в
`config.yaml` остаётся последняя успешная. Правка файла `config.yaml` руками на
лету не подхватывается — нужен перезапуск.

## Исполнители и связи

Дизайн: `../docs/superpowers/specs/2026-11-19-model-network-design.md`.

**Исполнитель** — модель Ollama со своим именем, описанием («когда ко мне
обращаться»), системным промптом и списком связей. В `config.yaml` это
`executors`; один из них `entry: true` — он отвечает первым. По умолчанию их два:
`dispatcher` (`gpt-oss:20b`, рассуждение `low`) и `big` («Большая модель», `deepseek-r1:8b`).

**Рассуждение** `reasoning: off | low | medium | high` (по умолчанию `off`; в приложении —
«Рассуждение»): сколько модель думает перед ответом. У `gpt-oss` уровень передаётся как есть
(`think: "low"` …); выключить рассуждение он не умеет, поэтому `off` для него — `low`. Остальным
моделям `off` — `think: false`, любой уровень — `think: true`. Текст рассуждения не звучит и не
попадает в историю. Замер волны 3: у `gpt-oss:20b` без уровня (средний) первый текст p90 — 2,8 с,
с `low` — 0,7 с. Модели без возможности `thinking` (Gemma, llama…) уровень не ломает: ядро узнаёт
возможности при сборке сети и шлёт им `think: false` (одно предупреждение в журнале на модель),
а если Ollama всё же ответит 400 про think — повторяет запрос без него и запоминает это.

**Обновление с прежних версий.** Диспетчер по умолчанию теперь `gpt-oss:20b` (рассуждение
`low`) вместо Gemma. Кто модель диспетчера не менял, после обновления получит новую: скачайте её
(`ollama pull gpt-oss:20b`, ~13 ГБ на диске и столько же памяти) — иначе каждый ход «модель
недоступна». С большой моделью (`deepseek-r1:8b`, ~5 ГБ) и Whisper (~1,6 ГБ) при `keep_alive`
24 ч это ~20 ГБ: на Mac с 16 ГБ будет подкачка или выгрузка моделей. Вернуть Gemma: в приложении
«Исполнители» → «Диспетчер» → «Модель» — выбрать
`fredrezones55/Gemma-4-Uncensored-HauhauCS-Aggressive`, «Рассуждение» — «Нет» (или то же в
`config.yaml`: `executors` с `model` и `reasoning: off` у `dispatcher`).

**Связь** `delegates: [{to, when}]` — «кому я могу передать задачу». В `when`
(«Когда вызывать») — условие, по которому модель решает, кому передать. Пустой
`when` — берётся описание цели; пусто и то и другое — связь неактивна, ядро её
модели не предлагает. Проверка настроек: id уникальны, цели существуют, на себя
передавать нельзя, одна цель — одна связь (иначе 422). Приложение при удалении
исполнителя убирает ссылки на него у остальных; ядро отклоняет настройки со
ссылкой на несуществующего исполнителя.

**Как идёт передача.** Для исполнителя с активными связями ядро само добавляет
в промпт правило и даёт модели инструмент `delegate(executor, task)`.
- Фраза до вызова («Минутку, сейчас узнаю») звучит сразу. Вызов без фразы —
  ядро говорит «Минутку, сейчас узнаю.» за модель; короткая фраза без вызова
  («Сейчас спрошу большую модель.»), если в ней глагол просьбы («спрошу»,
  «узнаю», «передам», «уточню»…) и имя ровно одной цели, передаёт сама
  (`auto: true`); задача — сам вопрос человека, без пометок обработчиков.
- Пока цель думает, колонка подаёт «думаю» каждые 8 с. Первый кусок ответа цели
  ждём до 90 с (`DELEGATE_FIRST_PART_LIMIT_S`), паузы между кусками — до 20 с.
- Цель недоступна, упала или промолчала — звучит «<Имя> сейчас не отвечает.»; не
  уложилась в предел — «Не получилось ответить вовремя, спроси попозже.»; ход помечен
  ошибкой, но тона ошибки после фразы нет.
- Глубина — не больше 2 передач (диспетчер → A → B); у исполнителя на глубине
  2 нет ни инструмента, ни правила передачи в промпте, цикл A ↔ B невозможен.
- Чтение ответа Ollama обрывается не раньше чем через 120 с
  (`REQUEST_TIMEOUT_S`): больше предела передачи и предела прогрева. Входному
  исполнителю раньше срабатывает свой предел первого куска — 45 с.
- Стиль `quiet` диспетчера переходит к цели. Ход с передачей хранит в истории
  сообщения (вопрос, фраза с вызовом `delegate`, ответ цели); цели получают
  плоский диалог.

**Страховка честности.** Ответ входного исполнителя ядро проверяет до озвучки первого
предложения (`network/guard.py`, `network/claim_check.py`). Нарушение — в ответе не было
вызова инструмента, а (a) человек в этом ходе попросил действие из закрытого списка (включи,
выключи, поставь, установи, запусти, останови, запиши, добавь, удали, убери, напомни, открой,
закрой, убавь, прибавь, переключи, зажги, погаси — и «включай», «включишь?», «можешь/могла бы
включить», «Включить свет»; не «узнай», «проверь», «расскажи», «можно ли …», не вопросы «как/
почему/когда …»; короткий ответ на уточнение, которого ждёт действие, — «Варёная» после «сухая
или варёная?» (инструмент переспросил или его не было) — продолжает прошлую просьбу, а ответ на
«Что-нибудь ещё?» после сделанного — нет), и
первое предложение голосом самого помощника говорит, что оно сделано или делается («Поставила
таймер», «Записал обед», «Понял, включаю музыку», «Сейчас включу свет») или называет состояние
того, что просили, и синонимов («Свет на кухне включён» на «включи», «Будильник установлен» на
«поставь», «Обед добавлен» на «запиши» — без «был/быть» и годов), (b) ответ пуст или (c) вызов
написан текстом (JSON `{"name": …}`, `timer_start(…)`, `<|…`). Тогда сказанное не звучит, а
модель прогоняется ещё раз с тем же диалогом (без нечестного ответа: с ним `gpt-oss:20b`
повторял ложь в 7 из 16 проб, без него — ни разу) и напоминанием «Ты не вызвал инструмент.
Вызови нужный инструмент или честно скажи, что не можешь это сделать.» Снова нарушение —
честная фраза: на просьбу действия «Не получилось это сделать — у меня нет подходящего
инструмента.», на пустой вопрос — «Не расслышала, повтори, пожалуйста.», иначе — «Не
получилось ответить, спроси ещё раз, пожалуйста.». Каждое срабатывание — строка INFO в журнале
и поле `guard: "retried" | "fallback"` в `turn_finished` (иначе `null`). Обычный ответ не
задерживается: первое предложение разговор и так копит целиком; утверждение держится до начала
вызова инструмента.
Не ловится (намеренно — лучше пропустить, чем переспросить честный ответ): факты и рассказ
(«Спутник был запущен в 1957 году», «МКС запустили…»), чужое лицо («ты поставил», «Кузя
включает»), отрицание и условное («не включила», «записала бы»), «Да, …» и «уже …» сразу после
хода с инструментом коннектора (подтверждение того вызова; передача delegate не в счёт), обратный
порядок слов («свет включаю», «таймер поставила»), «Давай включим…», просьба без глагола («Таймер
на пять минут»), выдуманные данные без глагола действия («на
улице +12°C»), «Поставлю таймер.» без «сейчас», ложь после вызова другого инструмента и не в
первом предложении. Ответы целей передачи не проверяются; пустой ответ после вызова инструмента
не повторяется (инструмент сработал бы дважды).

**Модели без инструментов.** Если модель не умеет вызывать инструменты
(`supports_tools: false` в `GET /models`), она отвечает как обычная, но сама
ничего не передаёт (связи ей не предлагаются). Как цели передачи инструменты
не нужны. Если модели нет в Ollama — «<Имя> сейчас не отвечает.» Если Ollama
не была запущена при старте ядра, умение инструментов неизвестно и передача
выключена; ядро спрашивает снова каждые 15 с и, как только узнает, пересобирает
сеть так же, как при правке настроек.

**Прогрев.** Остальные исполнители, кроме входного, греются в фоне после старта и
после каждой правки; итог — в `GET /status` → `executors: [{id, ready, error}]`
(не прогрелся — интерфейс пишет «модель недоступна»).

**Поменять «Большую модель».** В приложении: левая панель, «Исполнители», выбрать
«Большая модель», в поле «Модель» выбрать из списка Ollama (модель должна быть
скачана: `ollama pull <модель>`). Применяется на лету, без перезапуска; новая
модель сначала прогревается, старая выгружается после конца хода. Тем же
способом — через `PATCH /config` с `executors`.

**События и API.** `turn_finished` и `GET /turns` получили `path` (id
исполнителей по порядку, например `["dispatcher", "big"]`) и `delegations`
(список `{from, to, task, auto}`). `GET /config` отдаёт `executor_prompts` —
итоговые промпты всех исполнителей по id; `GET /models` — `supports_tools`.

### Облачные модели (OpenRouter)

Исполнитель может работать не в Ollama, а в облаке: `kind: cloud`, `model` — id модели
OpenRouter (`google/gemini-2.5-flash`, `deepseek/deepseek-chat-v3.1`, …). Ключ — в
интерфейсе («Облако» в настройках ядра) или в `config.yaml`:

```yaml
cloud:
  api_key: sk-or-…        # хранится только здесь, в ~/SmartEsp (не в git)
executors:
  - id: big
    name: Большая модель
    kind: cloud
    model: google/gemini-2.5-flash
```

- `GET /api/v1/config` показывает ключ как «•••»; «•••» в правке — «не менять». Через API
  меняется только `cloud.api_key`; `cloud.base_url` и `cloud.name` — только в `config.yaml`
  (иначе токен API позволил бы отправить ключ на чужой адрес). Другой сервис с
  OpenAI-совместимым API — свой `base_url`.
- Ответ идёт потоком (`chat/completions`, SSE); вызовы инструментов собираются из кусков.
  Рассуждение — `reasoning.effort` (`off` → `none`); модель, отклонившая его, дальше
  работает без поля. Ошибки звучат понятно: ключ не принят (401), нет денег (402), нет
  модели (404), предел запросов (429), нет сети.
- Прогрев только проверяет, что ключ задан: запрос к модели стоил бы денег.
- Умение инструментов не спрашивается у Ollama (в сети модель — `@cloud/<id>`); у какой
  модели инструментов нет, видно в списке `GET /api/v1/cloud/models` (кэш 10 минут; цены —
  доллары за 1 млн токенов).
- Текст разговора с этой моделью уходит в облако.

## Коннекторы

**Клиенты ядра** (`kind: client`, папка `clients/<id>`): та же запись в `connectors`, но это не MCP, а
обычная программа, которая ходит в API ядра (бот Telegram). Хаб её запускает и перезапускает, как
коннектор, передаёт `SMARTESP_URL` и `SMARTESP_TOKEN`, копит 200 последних строк её журнала и
понимает строки JSON `{"suggest": {"key", "value", "text"}}` — предложение дописать значение в
объявленную настройку-список (тип `pairs`, «ключ=значение;…»): в приложении — «Добавить».
Бот по умолчанию выключен.

Дизайн: `../docs/superpowers/specs/2026-11-19-mcp-hub-design.md`.

Возможности (заметки, счёт, таймеры, погода, питание) — MCP-коннекторы: отдельные
процессы, которые ядро запускает и с которыми говорит по stdio (модуль `tools/`).
Их инструменты получают исполнители, чья модель умеет инструменты
(`supports_tools`). Полный список по умолчанию — в `config.defaults.yaml`:

```yaml
connectors:
  - id: notes                  # папка данных: ~/SmartEsp/connectors/notes
    name: Заметки
    command: uv
    args: [run, --project, "{repo}/connectors/notes", notes-mcp]
    env: {}                    # дополнительные переменные окружения
    enabled: true
```

По умолчанию — наши из `connectors/` репозитория: `notes`, `calc`,
`timers`, `weather`, `food`, `web` (поиск в интернете и чтение страниц) и выключенные `mac_media` (музыка и звук Mac) и
`claude_tasks` (задачи Клоду). `mac_media` выключен, потому что модель зовёт его и
без просьбы (на «включи свет на кухне» — переключить звук на «кухню»); включают его
переключателем на панели коннектора или `{id: mac_media, enabled: true}` в
`config.yaml`. Звук он переключает только по точному имени устройства. `{repo}` в `command`, `args` и `env` ядро при запуске
заменяет на путь к репозиторию: настройки переживают его перенос (абсолютные пути
тоже работают).

В `config.yaml` коннекторы пишутся **по id и только изменённые поля** — остальное
берётся из умолчания с тем же id, а новые коннекторы новых версий приходят сами:

```yaml
connectors:
  - id: weather                # погоде нужно место; без него — «место не задано»
    env: {WEATHER_PLACE: Москва}
  - id: claude_tasks           # задачам Клоду нужны разрешённые папки (connectors/claude_tasks/README.md)
    enabled: true
    env: {CLAUDE_TASK_FOLDERS: "sandbox=/Users/я/claude-sandbox"}
  - id: food                   # убрать коннектор по умолчанию
    remove: true
  - id: my                     # свой коннектор: новый id, нужны name и command
    name: Моё
    command: /usr/local/bin/my-mcp
```

`env` сливается по ключам (`KEY: null` убирает ключ умолчания), `enabled: false`
выключает. Переключатель на панели коннектора в интерфейсе шлёт правку
`connectors: [{id, enabled}]` — она так же сливается по id, и ядро записывает в
`config.yaml` только отличия от умолчаний (полный список старого вида тоже читается
и при следующей записи сжимается до отличий). Через API (`PATCH /config`) у
коннектора можно менять **только** `enabled` у уже известного id и `env` — **только
ключи, которые коннектор объявил сам** (см. «Настройки коннектора» ниже):
`connectors: [{id, enabled?, env?: {КЛЮЧ: "значение" | null}}]` (`null` — вернуть
умолчание). Команда, аргументы, необъявленные ключи окружения, имя, новый коннектор,
`remove` и `connectors: null` — 422 «… меняют только в config.yaml» (иначе токен API
был бы запуском любой команды на Mac). Правка `config.yaml` руками может всё. В
`GET /config` непустые значения окружения с `TOKEN`, `KEY`, `SECRET` или `PASSWORD` в
имени ключа и ключей, объявленных коннектором как `secret`, заменены на `•••`.

**Настройки коннектора.** Коннектор объявляет, что владелец может менять в
приложении, файлом `smartesp.json` в папке своего проекта (её ядро берёт из
`--project` в `args`, после подстановки `{repo}`; у коннектора без `--project`
настроек нет). Файл только читается — через API он не меняется:

```json
{"settings": [
  {"key": "WEATHER_PLACE", "title": "Город", "type": "text", "hint": "например, Москва"}
]}
```

- `key` — переменная окружения: только заглавные `[A-Z][A-Z0-9_]*` и **со своим
  префиксом коннектора** — id заглавными, не буквы и не цифры заменены на `_`, плюс `_`
  (`weather` → `WEATHER_`, `mac_media` → `MAC_MEDIA_`, `web` → `WEB_`). Чужой ключ
  (`PS4`, `NODE_OPTIONS`, `PLACE`) файл объявить не может: ядро его пропускает с
  предупреждением в журнал (раз на ключ), в интерфейс он не попадает. `title` и `hint` —
  подпись и подсказка поля по-русски.
- `type`: `text` — строка; `path` — путь, начинается с `/` или `~/` (пусто — не задан);
  `list` — папки `имя=путь;имя=путь`: имена без повторов, пути с `/` или `~/` и папки
  должны существовать; `secret` — скрытое значение: в ответах `•••`, а `•••` в правке
  значит «не менять» (ключ с `TOKEN`/`KEY`/`SECRET`/`PASSWORD` в имени скрыт так же при
  любом типе); `flag` — `"1"` (включено) или `""`.
- Любое значение — строка до 500 символов в одну строку: без управляющих символов
  (NUL, табуляция, переводы строки, NEL и прочие C0/C1) и разделителей строк U+2028/2029.
- Вторая линия защиты — запрет без учёта регистра, даже при подходящем префиксе:
  `PATH`, `HOME`, `SHELL`, `ENV`, `IFS`, `TMPDIR`, `LANG`, `LC_*`, `VIRTUAL_ENV`,
  `SHELLOPTS`, `BASHOPTS`, `PS4`, `BASH_*`, `PYTHON*`, `DYLD_*`, `LD_*`, `UV_*`, `PIP_*`,
  `NODE_*`, `PERL5*`, `PERLLIB`, `RUBY*`, `GIT_*`, `XDG_*`, `SSL_*`, `REQUESTS_CA_BUNDLE`,
  `CURL_CA_BUNDLE`, `*_PROXY`, `ANTHROPIC_*`, `SMARTESP_*` (запуск кода через `sh -c`,
  он же bash, `uv`, `node` и т. п.; перехват трафика; чужие настройки программ).
- Необязательные `note` и `example` — пояснение для панели коннектора и пример записи в
  `config.yaml` (только показ), например почему настроек в приложении нет.

`GET /connectors` отдаёт у каждого коннектора `settings` —
`[{key, title, type, hint, value}]` с текущими значениями (секрет — `•••`), `note` и
`example`; в `GET /status` их нет. Сохранение — та же правка `connectors`, она применяется на лету
и перезапускает только этот коннектор. Сейчас объявлены: `weather` (`WEATHER_PLACE`,
`WEATHER_LAT`, `WEATHER_LON`) и `food` (`FOOD_OFF`). `claude_tasks` намеренно не
объявляет ничего (только `note` и `example`): папки и инструменты Клода через токен API
дали бы правку любых файлов (`~/.zshrc`) или оболочку — они настраиваются только в
`config.yaml`. `notes`, `calc`, `timers` и `mac_media` настроек не имеют.

Коннекторы стартуют в фоне: голос готов, не дожидаясь их, а пока коннектор
запускается, его инструментов в сети нет. Когда список готовых инструментов
меняется (коннектор встал, упал, выключен), сеть исполнителей пересобирается —
не чаще раза в 2 с, в той же очереди, что правки настроек (после них), и без
прогрева моделей: модели те же, а выгруженная кнопкой «Выгрузить» модель так и
остаётся выгруженной до следующего хода (греются только старт и правка исполнителей); не
вышло — повтор через 15 с, 60 с, … до 5 мин. Упавший коннектор перезапускается (1 с, 5 с, 30 с, дальше
раз в 5 мин). Правка `connectors` применяется на лету: изменённые
перезапускаются, убранные останавливаются. Коннектор просит сказать вслух
(таймер сработал) — объявление звучит на последней активной колонке, а если
после старта ядра никто не говорил — на первой подключённой (по имени). Состояния —
`GET /connectors` (с настройками) и `connectors` в `GET /status`.

**Инструменты в истории.** Вызовы инструментов входного исполнителя (диспетчера)
хранятся в истории хода вместе с ответами коннектора (ответ — до 600 символов), перед
текстом ответа: так модель в следующих ходах видит, что действие действительно
выполнено, и не «выполняет» просьбы одними словами. Вызовы цели передачи в историю не
попадают — там уже стоит её ответ. Участникам с инструментами ядро добавляет к промпту
правило: о сделанном говорить, только если инструмент вернул успех, вопрос инструмента
задавать человеку, ошибку — передавать; «нет доступа» — только когда просят действие или
данные без подходящего инструмента, а на разговор и общие знания отвечать как обычно.

**Живая подсветка.** Пока идёт ход, ядро шлёт `executor_active`
(`{turn_id, device_id, executor, state}`, `state` — `thinking`: ждём первый текст,
`speaking`: ответ звучит, `done`: закончил или передал задачу) и `tool_call`
(`{turn_id, device_id, executor, connector, tool, state, ok}`, `state` — `started`
или `finished`). Законченные вызовы попадают в `turn_finished` полем `tools`
(`[{executor, connector, tool, ok}]`). Ответ, отложенный «на потом», отмечает
`done` своего исполнителя, когда договорит; его вызовы инструментов после конца хода
видны только событиями `tool_call` (в `tools` уже опубликованного хода не попадают),
а `speaking` у него значит «пишет текст для объявления». Какие модели сейчас в памяти Ollama —
`ollama.loaded` в `GET /status` (`ollama ps`); интерфейс перечитывает его раз в 5 с.

## Приложение и API

Ядро отдаёт интерфейс на `/` (собранный `ui/dist`; без сборки — страница с
командой сборки) и API на `/api/v1`. Колонки ходят на `/device` — без токена.

**Сборка интерфейса.** Интерфейс — отдельный проект `ui/` (нужен Node.js):
`cd ui && npm ci && npm run build`. Ядро отдаёт готовый `ui/dist`; после сборки
перезапустите ядро и обновите страницу. Подробности — в [`ui/README.md`](../ui/README.md).

**Токен.** Весь API закрыт токеном (нужен и с `127.0.0.1`). Ядро создаёт его при
первом старте в `~/SmartEsp/token` (права `0600`, `secrets.token_urlsafe(32)`).
HTTP — заголовок `Authorization: Bearer <token>`, WebSocket — `?token=<token>`.
Без токена или с чужим — 401 (для WebSocket закрытие с кодом 4401).

**Файл запуска.** Сразу после подъёма сервера ядро пишет
`~/SmartEsp/run/core.json` — `{"port": …, "pid": …, "started_at": …}`; по нему
приложение находит порт и pid. При остановке файл удаляется.

Примеры:

```
curl -H "Authorization: Bearer $(cat ~/SmartEsp/token)" http://127.0.0.1:8765/api/v1/status
curl -X PATCH -H "Authorization: Bearer $(cat ~/SmartEsp/token)" \
  -H "Content-Type: application/json" \
  -d '{"tts": {"kind": "vosk", "voice": "female_1"}}' http://127.0.0.1:8765/api/v1/config
```

Ресурсы (все пути — с префиксом `/api/v1`):

| Запрос | Что делает |
|---|---|
| `GET /status` | версия, `uptime_s`, `state` (`warming`, `ready`, `stopping`), Ollama (`reachable`, `loaded`), колонки, голос (`state`: `ready`, `downloading`, `failed`, `missing`), `applying`, `restart_required`, `executors` (`[{id, ready, error}]` — итог фонового прогрева исполнителей, кроме входного), `connectors` (как в `GET /connectors`) |
| `GET /connectors` | MCP-коннекторы в порядке настроек: `{id, name, state, tools, error}`; `state` — `starting`, `ready`, `failed`, `disabled`; `tools` — имена инструментов для модели (только у готового); `error` — текст последней ошибки |
| `GET /config` | `effective` — настройки целиком, `overridden` — изменённые ключи через точку (`tts.kind`), `restart_sections`, `dispatcher_prompt` — итоговый промпт диспетчера (`system_prompt` входного исполнителя + правила включённых обработчиков и передачи), `executor_prompts` — итоговые промпты всех исполнителей по id; секреты в `env` коннекторов — `•••`; только для чтения |
| `PATCH /config` | частичные настройки в форме `config.yaml`: словари сливаются вглубь, списки заменяются целиком, `null` сбрасывает ключ к умолчанию. Ответ `{change_id, status, error}`: `accepted` или `restart_required` — 200, `invalid` — 422 (неизвестный ключ, неверное значение, неизвестный вид `kind` у `stt`, `tts`, исполнителя или обработчика, в `connectors` — что-то кроме `{id, enabled}` известного коннектора), `stopping` — 503 |
| `GET /models` | модели Ollama: `{name, size_bytes, supports_tools}` (Ollama недоступна — 502) |
| `POST /models/unload` | `{name}` → 204: выгрузить модель из памяти Ollama. Только модель, которая сейчас в памяти (`status.ollama.loaded`), иначе 404: запрос выгрузки загрузил бы её. Ollama недоступна — 502. Имя — в теле: в именах моделей бывает `/`. Модель живого исполнителя загрузится снова на следующем ходе |
| `GET /voices` | голоса: `{kind, voice, title, size_mb, downloaded, current}` |
| `POST /voices/download` | `{kind, voice}` → 202, `{change_id, status: "accepted"}`; ход скачивания — события `voice_download`, `voice_ready`. Голоса нет в каталоге `GET /voices` — 422 (`status: "invalid"`, текст в `error`), ядро останавливается — 503 (`status: "stopping"`) |
| `POST /voices/preview` | `{kind, voice, style="normal", text=null}` → `audio/wav` (16 кГц, 16 бит, моно); голос не скачан (или ещё качается) — 409, неизвестный голос — 404, модель не озвучила образец — 500; тело ошибки `{detail}` |
| `GET /turns?limit=100` | последние ходы (данные `turn_finished`: `turn_id`, `device_id`, `device_name`, `text`, `annotations`, `style`, `answer`, `status`, `path`, `delegations`, `tools`, `at` — время конца хода в секундах Unix, `stt_ms`, `first_text_ms`, `first_audio_ms`, `origin` — `wake`, `listen`, `core` или `api`, у хода через API ещё `source` и `person`), от новых к старым; ядро хранит 100 последних в памяти |
| `POST /ask` | ход через API текстом: `{text, person="", source="api"}` → `{answer, turn_id}` (см. «Ход через API») |
| `POST /ask/voice` | ход через API голосом: multipart `audio` (OGG/Opus или WAV, до 10 МБ), `person`, `source` → `{answer, turn_id}` |
| `POST /devices/{id}/play` | звуковой файл на колонке: multipart `audio` (MP3, WAV, OGG, M4A, FLAC; до 50 МБ) → 202 `{status: "started"}` (см. «Файл на колонке») |
| `DELETE /devices/{id}/play` | остановить файл на колонке → `{stopped}` (`false` — файл не играл); колонки нет — 404 |
| `GET /access` | `{urls}` — адреса `http://<ip>:<порт>/?token=…` для входа с других компьютеров сети (без `127.*`) |
| `GET /core` | `{version, uptime_s, state, port, data_dir}`; `port` — из настроек `server.port` |
| `POST /restart` | перезапуск ядра, ответ 202 |
| `POST /core/stop` | честная остановка и выход с кодом 0, ответ 202; приложение такое ядро не перезапускает |
| `WS /logs?token=` | журнал ядра: сначала последние 500 строк, затем новые; сообщение — JSON `{"at", "level", "text"}` (`level` — `INFO`, `WARNING`, `ERROR`…; токен из `?token=` спрятан). Медленный клиент теряет самые старые строки (очередь — 1000), память не растёт |
| `WS /events?token=` | поток событий JSON `{"kind", "data", "at"}`: `core_state`, `device_connected`, `device_disconnected`, `wake`, `arbitration`, `turn_started`, `turn_heard`, `executor_active`, `tool_call`, `turn_finished`, `change_applied`, `voice_download`, `voice_ready`, `playback_started`, `playback_finished` |

Схема OpenAPI для интерфейса: `uv run python -m smartesp --openapi ../ui/openapi.json`.

### Ход через API

`POST /api/v1/ask` и `POST /api/v1/ask/voice` — разговор с Кузей не с колонки, а
программой (Telegram-бот, скрипт). Ход идёт тем же путём, что с колонки:
обработчики (время и др.), сеть исполнителей с инструментами и передачами,
общая история, — но без звука: ответ приходит текстом.

- **Текст:** `{"text": "Который час?", "person": "Аня", "source": "telegram"}`.
  `text` — непустой (до 8000 символов); `person` — кто спрашивает (одна строка до 64
  символов, можно пусто); `source` — откуда (`a-z`, цифры, `_`, `-`; по
  умолчанию `api`).
- **Голос:** `multipart/form-data` с файлом `audio` (OGG/Opus, как у Telegram,
  или WAV; до 10 МБ) и полями `person`, `source`. Звук разбирает `ffmpeg`
  (ищется в `PATH`, затем `/opt/homebrew/bin`, `/usr/local/bin`;
  `brew install ffmpeg`) в 16 кГц моно (не длиннее 2 минут), дальше — то же распознавание, что у
  колонок.
- **Ответ 200:** `{"answer": "…", "turn_id": "api7"}`. Нечего распознать — честное
  «Не расслышала.»; исполнитель не ответил — «Не получилось ответить, попробуй
  ещё раз.».
- **Срок:** весь ход — не дольше 55 с (клиенту хватает своих 60 с), включая
  передачу задачи большой модели. Не уложились — к сказанному добавляется
  «Не успела ответить, спроси попозже.»; запоздавший ответ не откладывается и
  на колонках не объявляется.
- **Очередь:** одновременно — не больше двух ходов через API (модель общая с
  колонками); третий вопрос ждёт места до 10 с (в счёт своих 55 с), не дождался —
  503 «Кузя занят другими вопросами, спроси чуть позже».
- **Ошибки:** 401 — токен (у `/ask` и `/ask/voice` он проверяется до чтения
  тела); 413 — тело больше предела (`/ask` — 64 КБ, `/ask/voice` — 10 МБ звука;
  у остальных запросов общий предел 12 МБ; лишнее не читается; путь с управляющими
  символами — 400); 422 — неверный запрос или
  звук не разобрать (`{"detail": "…"}` по-русски); 503 — ядро ещё греется,
  останавливается или нет `ffmpeg`.
- **Лента:** ход виден как обычный, с `origin: "api"`, источником вместо колонки
  («Telegram») и именем человека; номера ходов свои — `api1`, `api2`, … Ходы
  через API идут параллельно с ходами колонок и им не мешают.
- **История** общая с колонками, но вопрос записывается в неё с пометкой
  источника — `[Telegram · Аня] текст`, — чтобы в следующих ходах (и дома) было
  видно, кто и откуда спрашивал.

```
curl -H "Authorization: Bearer $(cat ~/SmartEsp/token)" -H "Content-Type: application/json" \
  -d '{"text": "Который час?", "person": "Аня", "source": "telegram"}' http://127.0.0.1:8765/api/v1/ask
curl -H "Authorization: Bearer $(cat ~/SmartEsp/token)" -F audio=@voice.ogg -F person=Аня \
  -F source=telegram http://127.0.0.1:8765/api/v1/ask/voice
```

**Telegram-бот** — отдельная программа-клиент этого API (`../clients/telegram/`):
создать бота, вписать токены и допущенных людей и запустить — по
[`clients/telegram/README.md`](../clients/telegram/README.md). Коротко: ядро
запущено, затем `cd clients/telegram && uv sync && uv run telegram-bot`.

### Файл на колонке

`POST /api/v1/devices/{id}/play` проигрывает звуковой файл на колонке — общий
механизм (проверить звук, позже — для коннекторов), а не «музыка» в ядре.

- **Файл:** `multipart/form-data` с файлом `audio` — MP3, WAV, OGG, M4A или FLAC,
  до 50 МБ (токен и размер проверяются до чтения тела). `ffmpeg` разбирает его
  по ходу в 16 кГц моно (не длиннее 15 минут): звук идёт на колонку кусками, а не
  после разбора всего файла. Пока файл играет, загрузка лежит во временном файле.
- **Как играет:** ходом ядра, как объявление: колонка сначала сыграет «внимание».
  На колонке — один файл за раз; слово пробуждения на ней прерывает файл.
  Объявление (таймер, речь по инициативе) вытесняет файл: файл останавливается
  (`interrupted`) и не возобновляется, объявление звучит сразу. Пока колонка занята
  разговором, очередь объявлений ждёт, не синтезируя речь впустую. Ход файла — не
  дольше 15 мин 30 с по часам.
- **Ответ 202** `{"status": "started"}` — колонка начала получать звук. Итог —
  события `playback_started {device_id}` и `playback_finished {device_id, delivery}`,
  `delivery` — `delivered`, `interrupted` (перебили словом или остановили), `busy`,
  `lost`.
- **Ошибки** (`{"detail": "…"}` по-русски): 404 — колонки нет; 409 — колонка не в
  сети, её прошивка не умеет речь по инициативе (протокол < 3), на ней уже играет
  файл или идёт разговор, файл остановили до начала; 413 — файл больше 50 МБ; 422 — файл пуст или не
  разобрать; 503 — нет `ffmpeg` или ядро останавливается.
- **Остановить:** `DELETE /api/v1/devices/{id}/play` — колонке уходит `cancel_turn`,
  итог `interrupted`. Файл ещё загружается — он не начнётся (`{stopped: true}`, его
  POST получит 409).
- Тело multipart FastAPI разбирает до обработчика: отказ по колонке (404/409)
  приходит уже после загрузки файла (под токеном, до 50 МБ).

```
curl -H "Authorization: Bearer $(cat ~/SmartEsp/token)" -F audio=@song.mp3 \
  http://127.0.0.1:8765/api/v1/devices/AA:BB:CC:DD:EE:FF/play
```

## Остановка и перезапуск

Остановка (Ctrl+C, SIGTERM, закрытый stdin при `--parent-watch`, `POST /core/stop`
или `POST /restart`) идёт по порядку и занимает не дольше 15 с:

1. состояние `stopping`; новые фразы и правки настроек не принимаются: колонка
   на фразу получает отмену хода (`cancel_turn`), правка — ответ 503. Колонки
   при этом могут подключаться, пока их не отключат на шаге 3;
2. идущие ответы договариваются — до 10 с, потом обрываются; одновременно
   закрываются коннекторы: не закрылся за 2 с — его процессы убиваются;
3. очередь объявлений (речь по инициативе) бросается, колонки отключаются;
4. каждая загруженная модель выгружается из Ollama — все одновременно, не дольше 1 с;
5. файл `run/core.json` удаляется, процесс выходит с кодом 0.

Просьбы во время остановки её не прерывают, а только уточняют итог: `POST /restart`,
`POST /core/stop`, первый сигнал или закрытый stdin. Остановка (`POST /core/stop`,
сигнал, stdin) важнее перезапуска. Немедленный выход — только по второй просьбе о
выходе: повторный Ctrl+C/SIGTERM (в том числе сигнал после закрытого stdin).

`POST /restart` делает ту же остановку и затем запускает ядро заново (с теми же
флагами). Если одновременно пришла просьба выйти (сигнал, закрытый stdin,
`POST /core/stop`), перезапуска нет — ядро просто выходит.

## Речь по инициативе

Дизайн: `../docs/superpowers/specs/2026-11-19-proactive-speech-design.md`.

Кузя может заговорить сам — например, сказать запоздавший ответ большой модели.
Объявление ставится в очередь колонки (модуль `notify/`) и звучит, когда колонка
свободна: сигнал «внимание» (его играет сама колонка, приняв `announce`), затем
речь. Колонка — та, на которой спрашивали; не подключена — последняя активная;
нет и той — первая подключённая (по имени); нет никакой — объявление ждёт, пока
какая-нибудь подключится. На колонке идёт ход — ждём его конца (звучащий ответ мягко
прерывается, см. ниже); связь оборвалась или колонка ответила `busy` — повтор каждые 5 с; не
доставлено за 10 мин — снимается, в ленте «не доставлено». Перебили словом
словом пробуждения («Миранда») — считается услышанным, не повторяется. Объявления одной колонки звучат по
порядку. Нужна прошивка с протоколом 3; очередь не переживает перезапуск ядра.

Раздел `speech` в `config.yaml` (применяется на лету):

```yaml
speech:
  proactive: true              # «Кузя может заговорить сам»: запоздавший ответ — объявлением
  listen_after_question: true  # кончил речь вопросом — колонка слушает ответ без слова пробуждения
```

В ленте (`turn_finished`) объявление — `kind: "announcement"`, `origin: "core"`,
`turn_id: "a<n>"`, текст в `answer`, итог `status`: `ok`, `interrupted` или
`undelivered`.

### Мягкое прерывание

Результат отложенной задачи (запоздавший ответ модели, объявление коннектора — пока
все они высокого приоритета) приходит, а колонка говорит ответ, начатый раньше
результата: ответ перестаёт получать новые предложения. Отправленное колонка
договаривает — слово не обрывается: колонке уходят только целые предложения и не
больше 3 с звука впереди услышанного (услышанное — по событию `played` прошивки
0.4.0, у старой прошивки — по оценке темпа), затем `reply_end`. После `playback_done`
звучит «Кстати, готово: …» (следующие результаты из той же очереди — «И ещё: …»), а в
конце — «Вернёмся к тому, о чём говорили?», и колонка слушает. «Да» («давай»,
«продолжай») — Кузя продолжает с первого непрозвучавшего предложения (модель к этому
времени дописывает ответ в фоне); любой другой ответ — обычный ход, остаток забыт.
Остаток ждёт 5 минут. Человек говорит или модель ещё думает — ход не прерывается:
объявление ждёт его конца (проверка 4 раза в секунду). В ленте прерванный ход —
`interruption: "paused"`, продолжение — `interruption: "resumed"`.

## В работе

Что сейчас делается в фоне — реестр «В работе» (модуль `tasks/`): ожидание
запоздавшего ответа модели (источник `late_answer`) и задачи коннекторов
(`connector:<id>`: идущие таймеры с временем срабатывания, задачи Claude Code).
Коннектор сообщает о задаче уведомлением журнала MCP `{"type": "task", "id",
"title", "status", "eta", "person", "result"}` (поля — в
`../docs/superpowers/specs/2026-11-19-mcp-hub-design.md`); упал или выключен — его
идущие задачи отменяются. `GET /api/v1/tasks` — идущие задачи (старые первыми) и
законченные за последние 2 минуты; события `task_started`, `task_updated`,
`task_finished` (данные — те же поля). В интерфейсе — раздел «В работе» в левой
панели.

## Обучение моделей

Наборы для обучения — папки `trainers/<id>/` репозитория (описание `smartesp.json`: название,
подсказка записи, цели по умолчанию). Цель — отдельная модель: «Откликаться на» (`positive`) и
«Не откликаться на» (`negative`); владелец правит цели во вкладке «Обучение»
(`~/SmartEsp/training/<набор>/targets.json`).

Запись с колонки: `POST /api/v1/training/<набор>/record {device_id, phrase, person}` — колонка
(протокол 3) пикает и слушает до паузы, как после вопроса; фраза не идёт в разговор и в ленту, ход
кончается пустым ответом. Файл — `~/SmartEsp/training/<набор>/recordings/<фраза>/<человек>/NNNN.wav`
(16 кГц, моно; тот же микрофон и шумоподавление, что у слова пробуждения). Ответ — имя, длительность
и пик громкости; 409 — колонка не подключена, занята или со старой прошивкой; 422 — речи не было.
Ещё: `GET /api/v1/training` (наборы, цели, сколько записей у кого), `PUT …/targets`,
`GET|DELETE …/recordings/<имя>?phrase=&person=`.

Шаги обучения (описаны в `smartesp.json` набора: `command` и `steps[{id, title, hint, per_target, args}]`,
подстановки `{kit}`, `{repo}`, `{target}`, `{run}`) ядро запускает подпроцессом — по одному за раз
(обучение занимает весь процессор): `POST …/steps/<шаг> {target, run}` (202; занято — 409),
`GET …/job` — ход (стадия, сколько из скольки), последние 300 строк журнала, итог; `DELETE …/job` —
остановить (SIGTERM группе, через 10 с SIGKILL); `GET …/runs` — итоги прогонов (`result.json`).
Набор пишет ход строками JSON в stdout, журнал — в stderr. Шаг получает ту же папку данных
(`SMARTESP_HOME`) и `uv` ядра (`UV`); при остановке ядра идущий шаг останавливается. Дизайн —
`docs/superpowers/specs/2026-11-22-training-design.md`.

## Колонки

Колонка представляется ядру MAC-адресом Wi-Fi: `device_id` в `hello`,
заглавными через двоеточие (`AA:BB:CC:DD:EE:FF`). MAC видно в журнале ядра при
подключении: `device AA:BB:CC:DD:EE:FF connected from …`. Имя колонки (модель
его видит: «Колонка: Кухня») задаётся в `config.yaml`, ключ — MAC **в кавычках**:
MAC из одних цифр без кавычек YAML прочтёт как число, и ядро не запустится
(«неверные настройки»).

```yaml
devices:
  "AA:BB:CC:DD:EE:FF":
    name: Кухня
  "11:22:33:44:55:66":
    name: Спальня
```

## Обработчики фразы

Обработчики смотрят на фразу и добавляют пометки в промпт модели; список — `stages`
в `config.yaml`. Пометки идут модели не внутри слов человека, а отдельными сообщениями
`system` прямо перед ними: так модель не переносит их в параметры инструментов (имя
таймера «Кухня», время еды «вечер»). В историю попадают только слова человека.

- **Справка** — время и имя колонки, одной строкой: «Справочные данные — только для
  инструментов и прямых вопросов, к разговору не относятся. Не упоминай их в ответе,
  если человек о них не спросил: время — четверг, 19 ноября 2026, 18:19; колонка —
  Кухня.» Без этого модель вставляла время в обычные ответы («в этот вечер», «Чем могу
  помочь, Кухня?»). Проба на диспетчере (12 обычных вопросов × 4 прогона): упоминаний
  5/48 → 0/48; «Который час?» верно 12/12 → 12/12; параметры таймера и еды чистые.
- **Пометки к реплике** — остальное («Пометки к следующему сообщению человека: …»).

Сейчас обработчики такие:

- `clock` — время: справка с днём недели, датой и временем (без части суток: слово
  «вечер» модель охотнее всего переносила в ответы).
- `system` — система: справка «в работе — Таймер «картошка» (ещё 7 мин)» (или
  «ничего», не больше 5 задач) и «навыки — Заметки, Погода, …» (готовые коннекторы).
  Модель отвечает на «что сейчас делается?» и «что ты умеешь?», не гадая. Данные даёт
  связка (`wiring.py`): реестр «В работе» и состояния коннекторов. Настройки версии 4
  при переходе на 5 получают `system` в сохранённый список `stages` (один раз).

**Конец разговора.** Реплика только из слов прощания («всё, пока», «спасибо, хватит»,
«спокойной ночи», «больше ничего не нужно») до модели не доходит: ход кончается молча,
без вопроса и без записи в историю (`conversation/farewell.py`). Вопрос-предложение
помощи в конце ответа («Чем могу помочь?», «Что-нибудь ещё?») не озвучивается: после
него колонка снова слушала, и разговор не кончался. Промпт по умолчанию — правила по
пунктам (инструменты первыми, «сделала» только по ответу инструмента, без вопросов в
конце, на прощание — «Пока!»); проба на `gpt-oss:20b` и `qwen3:8b` с инструментами:
заметки и счёт — через инструмент, «включи свет» без инструмента — «Этого я пока не
умею», «что сейчас делается?» — по справке.
- `whisper_detect` — шёпот. Вопрос сказан шёпотом (слово «Миранда» — обычным
  голосом) → у хода в ленте пометка «Сказано шёпотом». Текст вопроса не меняется:
  распознаётся как обычно. В журнале на каждую фразу: `шёпот: да/нет (… доля тона 0.85)`.
  **Тихий ответ** (`quiet_reply`) по умолчанию выключен: ни один голос не умеет
  настоящий шёпот, «тихо» — просто громкость ниже, а правило про метку
  `[style:quiet]` модель применяла и без шёпота (проба: 5 из 72 обычных ответов с
  меткой; без правила — 0 из 72). Включить — в интерфейсе («Отвечать тише на шёпот»
  в панели обработчика) или в `config.yaml`:

  ```yaml
  stages:
    - kind: whisper_detect
      quiet_reply: true
    - kind: clock
  ```

  Тогда пометка «Человек говорит шёпотом» идёт модели, она начинает ответ меткой
  `[style:quiet]`, и колонка отвечает тише; у хода — `стиль quiet`.

  Точность (замер 2026-11-20, синтетика: 10 голосов ядра — Silero, Piper, Vosk — × 6
  фраз; живых записей шёпота нет). Ложные срабатывания на обычной речи — 0 из 240
  (чисто, тихо −40 дБ, комната с отзвуком и шумом, издалека −38 дБ с шумом 8 дБ;
  наименьшая доля тона 0.21 при пороге 0.15). Попадания на приближении шёпота
  (огибающая той же речи, возбуждение — шум вместо тона) — 35 из 120: детектор
  осторожный, громкий или близкий к микрофону шёпот часто не замечает. Порог 0.20
  дал бы 75 из 120 без ложных на этом наборе, но запас до обычной речи «издалека»
  тогда 0.01 — оставлен 0.15. Распознавание текста от этого не зависит: тот же STT
  разобрал 60/60 фраз тихой речи и 60/60 — приближения шёпота. Ядро тихую речь не
  отбрасывает (порогов громкости в нём нет); начало и конец фразы на колонке
  определяет VAD прошивки — как он ведёт себя на тихом шёпоте, не проверялось.

Обработчики включены по умолчанию; выключить все — `stages: []`. Правила для модели
(например, про метку `[style:quiet]`) обработчик приносит сам: ядро добавляет правила
включённых обработчиков к системному промпту диспетчера, в настройках их писать не нужно.

## Где что лежит

Папка данных — `~/SmartEsp` (или `$SMARTESP_HOME`):
- `config.yaml` — ваши изменения настроек (колонки, модели, голос…);
- `config.defaults.yaml` — все значения по умолчанию, для справки;
- `token` — токен API (права `0600`);
- `run/core.json` — порт и pid работающего ядра (есть только пока ядро запущено);
- `voices/` — скачанные голоса (Piper, Silero, Vosk);
- `logs/core.log` — журнал (5 файлов по 1 МБ, плюс вывод в консоль). Каждый
  ход — строка с вопросом, ответом и задержками `stt_ms`, `first_text_ms`,
  `first_audio_ms`.

## Проверка без колонки

Поддельная колонка задаёт вопрос из WAV (16 кГц, 16 бит, моно) и печатает
ответ ядра (из корня репозитория, при запущенном ядре):

```
uv run --project core python tools/fake_device.py --wav core/tests/data/privet.wav --out reply.wav
```

Колонка ведёт себя как прошивка: «играет» ответ столько, сколько он звучит, и
шлёт `playback_done`; выходит, пробыв в покое `--linger` секунд (по умолчанию 3).
Ответы сохраняются в `reply.wav`, `reply-2.wav`… WAV с фразой делает
`tools/make_wav.py` (голос Silero).

### Речь по инициативе (протокол 3)

С `--protocol 3` колонка понимает ходы ядра: на `listen` шлёт звук очередного
`--answer-wav` (ответы кончились — `utterance_end no_speech` через 5 с), на
`announce` принимает объявление (печатает «♪ внимание» — этот сигнал колонка
играет сама, приняв объявление) и доигрывает его; не в покое — отвечает `busy`
молча.

Слушать после вопроса — Кузя переспрашивает, колонка отвечает «Синий»:

```
uv run --project core python tools/make_wav.py "Спроси меня, какой мой любимый цвет." q.wav
uv run --project core python tools/make_wav.py "Синий." a.wav
uv run --project core python tools/fake_device.py --protocol 3 --wav q.wav --answer-wav a.wav --linger 8
```

Ожидается: ответ Кузи с «?» → `playback_done` → `listen` → ответ «Синий» → второй
ход; в `GET /api/v1/turns` у него `"origin": "listen"`.

Объявления — колонка без вопроса ждёт речи ядра (запоздавший ответ цели
передачи приходит не раньше, чем через 90 с после вопроса):

```
uv run --project core python tools/fake_device.py --protocol 3 --linger 300
```

`--busy` — колонка на каждый `announce`/`listen` отвечает `busy` (ядро повторяет
объявление каждые 5 с, `listen` молча снимается).
