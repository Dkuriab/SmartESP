# Речь по инициативе Кузи — дизайн

Дата: 2026-11-19. Дополняет дизайн ядра (`2026-11-18-core-design.md`, раздел 7.3)
и дизайн сети моделей (`2026-11-19-model-network-design.md`, раздел 7а).

## 1. Зачем

Владелец: Кузя должен сам заговаривать на колонке — сообщать о выполненных
задачах и что-то спрашивать. Это настройка, по умолчанию включена.

Сегодня единственная «задача в фоне» — ответ большой модели, который не уложился
в 90 с: ход заканчивается фразой «Не получилось ответить вовремя, спроси
попозже», ответ теряется. Напоминаний и фоновых задач ещё нет (этап 5). Поэтому
делаем общий канал «сказать на колонке», а первым пользователем станет
запоздавший ответ.

Отдельно владелец: «в дальнейшем потребуется активация программно, не только
через обращение». Поэтому включение микрофона ядром — отдельная команда прошивки,
а не частный случай «после вопроса».

## 2. Цели, не-цели, анти-цели

**Цели**
- Запоздавший ответ звучит сам, когда готов.
- Кузя задал вопрос — колонка слушает ответ без слова «Кузя».
- Ядро умеет включить микрофон на свободной колонке в любой момент.
- Звуки колонки — приятные, а не голые синусоиды.
- Две настройки в приложении, обе включены по умолчанию.

**Не-цели (позже, см. `docs/backlog.md`)**
- Напоминания, фоновые задачи, агенты (этап 5) — они будут пользоваться этим
  каналом, но сами не делаются.
- Тихие часы.
- Загрузка своих звуков из приложения, прошивка по воздуху.
- Отмена запоздавшего ответа голосом («Кузя, не надо»).
- Адресация человеку («скажи Маше»), а не колонке.

**Анти-цели**
- Колонка не должна заговорить посреди чужого разговора или перебить себя.
- Кузя не должен пугать: речь по своей инициативе начинается со звука «внимание».
- Микрофон не должен включаться незаметно: перед прослушиванием всегда звук.
- Старая прошивка не должна ломаться: колонка без новых команд работает как
  раньше, а речь по инициативе на ней просто не включается.

## 3. Подходы

**Прошивка: как ядро включает микрофон.**
1. *Отдельная команда `listen`* (выбрано): ядро может включить микрофон на
   свободной колонке в любой момент. После вопроса ядро ждёт `playback_done` и
   шлёт `listen`. Цена — сотые доли секунды паузы; слово «Кузя» в этот момент
   просто начнёт новый ход.
2. *Пометка «слушай после» в `reply_end`*: без паузы, но микрофон включается
   только после речи Кузи — программной активации нет. Отклонено: не закрывает
   просьбу владельца.

К обеим командам (`announce`, `listen`) прошивка добавляет ответ `busy`, если
колонка занята: сейчас `announce` в занятом состоянии молча пропадает, и ядро
не знает, что надо повторить.

**Ядро: где живёт отложенная речь.** Разумный путь один — отдельный модуль
«очередь речи» (`notify/`, он уже назван в дизайне ядра): ядро кладёт туда
«сказать X на колонке Y», модуль ждёт, пока колонка свободна, повторяет,
снимает просроченное. Держать обычный ход открытым минутами нельзя: у колонки
таймаут ответа, и она была бы занята всё это время.

## 4. Как это звучит

**Запоздавший ответ** (настройка «Кузя может заговорить сам» включена):
1. «Кузя, …сложный вопрос» → «Минутку, сейчас узнаю» → звуки «думаю».
2. Цель передачи не дала первый кусок за 90 с → Кузя говорит
   **«<Имя> долго думает. Скажу, когда будет готово.»** Ход заканчивается
   обычным образом (не ошибка), колонка свободна.
3. Ответ готов → звук «внимание» → **«Ответ от <Имени>: …»** (весь ответ цели).
4. Ответ попадает в историю: «Кузя, а подробнее?» работает.

Если настройка выключена — как сейчас: «Не получилось ответить вовремя, спроси
попозже.» Если колонка старая (протокол < 3) — тоже как сейчас.

**Вопрос Кузи** (настройка «Слушать после вопроса» включена): любая реплика
Кузи, последнее предложение которой кончается на «?» — и в обычном ходе, и в
речи по инициативе. После того как колонка доиграла, звучит «слушаю», колонка
слушает до 5 с. Заговорили — обычный ход (история уже содержит вопрос Кузи).
Тишина — колонка молча возвращается к ожиданию слова.

Ход прерван (перебили словом, отменён) — прослушивание не включается.

## 5. Прошивка

### 5.1 Протокол v3

`hello` → `protocol: 3`. Ядро шлёт `listen` и рассчитывает на `busy` только
колонкам с протоколом ≥ 3; колонкам v2 речь по инициативе не шлётся.

| Направление | `type` | Поля | Смысл |
|---|---|---|---|
| ядро → ESP | `announce` | `turn` | как в v2; в занятом состоянии теперь отвечает `busy` |
| ядро → ESP | `listen` (новое) | `turn` | из `Idle`: звук «слушаю», запись, дальше как ход по слову (звук + `utterance_end{turn}`), но без `wake` |
| ESP → ядро | `busy` (новое) | `turn` | `announce`/`listen` не приняты: колонка не в `Idle` |
| ядро → ESP | `tone` | `name` | новые имена: `listen`, `attention` |

Номера ходов для `announce` и `listen` выдаёт ядро, со старшим битом
(`0x80000000 | n`), как в v2.

`listen` без речи → `utterance_end{reason: no_speech}`, как после слова.
Таймаут без речи — тот же `noSpeechTimeoutMs` (5 с).

### 5.2 Session

- `Listen` в `Idle` при связи → `SetActiveTurn(turn)`, звук `Listen`,
  `StartCapture`, состояние `Listening` (с теми же таймаутами, что после слова).
- `Announce`/`Listen` не в `Idle` → действие «отправить `busy{turn}`».
- Остальное не меняется: перебивание словом, `cancel_turn`, потеря связи.
- Тесты `tools/host_tests/session_test.cpp` и `protocol_test.cpp`: listen из
  покоя, listen/announce в занятом состоянии → busy, listen без речи, слово
  во время listen-хода.

### 5.3 Звуки

Сейчас тоны — синусоиды без огибающей: щелчки в начале и конце, резкий звук.

- Звуки синтезирует программа `tools/make_sounds.py` на Mac (мягкие колокольчики:
  несколько гармоник, быстрая атака, экспоненциальное затухание, без щелчков) и
  пишет их как массивы PCM 16 кГц / 16 бит в `src/audio_out/SoundData.cpp`
  (сгенерированный файл, правится только программой).
- `AudioOut` проигрывает звук из массива с текущей громкостью вместо генерации
  синусоиды.
- Набор: `Wake` («слушаю» после слова), `Listen` (тот же «слушаю» — колонка
  слушает, неважно почему), `Thinking`, `Error`, `Attention` (перед речью по
  инициативе). Длина — до 0,6 с, `Thinking` — короткий, он повторяется.
- Вкус звуков — на усмотрение исполнителя (владелец: «на свой вкус»). Свои
  звуки владелец позже будет загружать из приложения (бэклог).

## 6. Ядро

### 6.1 Колонки (`devices/`)

`DevicePort` дополняется (договор в `contracts/device.py`):
- `supports_proactive(device_id) -> bool` — колонка подключена и протокол ≥ 3.
- `async announce(device_id, audio) -> Delivery` — `announce` + `reply_start` +
  звук + `reply_end` новым ходом ядра. Итог:
  - `delivered` — колонка доиграла (`playback_done`);
  - `interrupted` — на этой колонке сказали «Кузя» посреди объявления
    (`barge_in`) или ядро отменило ход: человек перебил сознательно, считаем
    услышанным, **не повторяем**;
  - `busy` — колонка ответила `busy`: повторить;
  - `lost` — обрыв связи или нет `playback_done` за срок воспроизведения + 15 с:
    повторить.
- Объявление не участвует в арбитраже: слово на другой колонке его не
  обрывает (там может быть другой человек в другой комнате).
- `async listen_after(device_id, turn) -> None` — ждёт `playback_done` хода
  `turn` и шлёт `listen`; ход закончился иначе (перебили, отменили, обрыв) или
  `busy` — ничего не делает.
- `last_active_device() -> str | None` — колонка последнего принятого хода.

Ход `listen` не проходит арбитраж (колонка одна, её выбрало ядро): его звук
сразу собирается в `Utterance`, как принятый ход. Слово на другой колонке во
время такого хода — обычное правило «новый ход побеждает».

`hub.py` уже 295 строк — новое кладётся в отдельные файлы модуля.

### 6.2 Очередь речи (`notify/`)

`Announcer` — очередь объявлений по колонкам.
- `say(device_id, text, *, source) -> None` — поставить в очередь. `source` —
  кто говорит (для ленты).
- Колонка: заданная; не подключена — `last_active_device()`; и той нет —
  ждём, пока какая-нибудь подключится.
- По одному объявлению на колонку за раз. Синтез (TTS) → `announce`. Перед
  речью — звук `attention` (ядро шлёт `tone attention` в начале хода
  объявления).
- `busy`/`lost` — повтор каждые 5 с; `interrupted` — снимается как услышанное. Не доставлено за 10 мин —
  снимается, событие «не доставлено».
- Доставлено и текст кончается вопросом, «Слушать после вопроса» включено —
  `listen_after`.
- Остановка ядра: очередь бросается (речь по инициативе не переживает
  перезапуск), фоновые задачи отменяются в пределах честной остановки.

### 6.3 Запоздавший ответ (`conversation/`)

- Предел 90 с (`DELEGATE_FIRST_PART_LIMIT_S`) остаётся. Когда он истёк, а
  речь по инициативе включена и `supports_proactive` колонки → вместо
  `TIMEOUT_PHRASE` звучит «<Имя> долго думает. Скажу, когда будет готово.»
  (без `failure`), ход заканчивается.
- Поток кусков цели не закрывается, а передаётся фоновой задаче «дождаться
  ответа»: она собирает весь ответ (предел 10 мин от начала хода, пауза между
  кусками — как сейчас `PART_IDLE_S`), затем `Announcer.say(колонка хода,
  "Ответ от <Имени>: " + ответ)`.
- В историю — отдельным обменом: вопрос хода и «Ответ от <Имени>: …», чтобы
  следующий ход видел ответ.
- Цель так и не ответила / сбой → объявление «<Имя> так и не ответил(а)…» не
  делаем: в ленту — событие «не дождались», вслух ничего. (Человек уже слышал
  «скажу, когда будет готово»; молчание хуже фразы, но фраза о сбое через
  10 минут без контекста ещё хуже. Решение исполнителя плана можно пересмотреть
  с владельцем.)
- Пока ждём запоздавший ответ, цель может получить новую передачу. Ollama
  обычно обрабатывает один запрос модели за раз, и новый встанет в очередь за
  прежним. Ничего особого не делаем: каждый вопрос получит свой ответ, второй
  может тоже уйти в «долго думает» и прозвучать вторым объявлением, по порядку.
  Без реестра ожиданий и новых фраз.
- Слушать после вопроса: в конце обычного хода, если последнее озвученное
  предложение кончается на «?», ход не прерван и настройка включена →
  `listen_after(device_id, turn)`.

### 6.4 Настройки

Новый раздел `config.yaml`:

```yaml
speech:
  proactive: true            # «Кузя может заговорить сам»
  listen_after_question: true  # «Слушать после вопроса»
```

Применяются на лету (как остальные разделы, через очередь правок). Раздел с
значениями по умолчанию — новые конфиги получают его сами; если нужна миграция
версии — по правилам `config/loader.py`.

### 6.5 Лента и интерфейс

- События: объявление поставлено / прозвучало / не доставлено; ход по `listen`
  отмечен как «ответ на вопрос Кузи».
- В ленте объявление — карточка реплики Кузи с пометкой «сам»; не
  доставленное — с пометкой «не доставлено».
- В настройках (раздел разговора) — два переключателя.
- Колонка v2 в списке колонок — подсказка «обновите прошивку, чтобы Кузя мог
  говорить сам» (тихая, не ошибка).

## 7. Решения, принятые без владельца (можно поправить)

- Слушать после вопроса — для любой реплики Кузи с «?» в конце, не только для
  речи по инициативе.
- Колонка вне сети → последняя активная; срок доставки 10 мин; повтор каждые 5 с.
- Тихих часов пока нет.
- Звук «слушаю» один и тот же после слова и после вопроса.
- Неудачный запоздавший ответ вслух не объявляется.
- Очередь речи не переживает перезапуск ядра.
- Перебили объявление словом «Кузя» на той же колонке — считается услышанным и
  не повторяется; слово на другой колонке объявление не обрывает.
- Второй вопрос той же модели, пока она ещё думает над первым, — просто ждёт
  своей очереди; ответы звучат по порядку.
