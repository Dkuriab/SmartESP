# SmartESP — дизайн ядра (домашний ассистент на Mac)

Статус: на согласовании. Прошивка — `2026-11-15-firmware-design.md`.

## 1. Зачем

Колонки на ESP32 уже слышат слово, пишут вопрос и играют ответ, но отвечать
им некому: есть только тестовый эхо-сервер. Нужно ядро на Mac, которое
превращает колонки в домашнего ассистента:

- отвечает голосом с помощью локальных нейросетей (Ollama);
- работает с несколькими колонками по дому;
- знает, кто говорит, и ведёт личные заметки/дела каждого;
- подключает внешние возможности (лампочки, заметки, напоминания, музыка)
  как отдельные плагины, не меняя ядро;
- состоит из сети моделей: маленькая быстрая отвечает сразу и решает,
  сделать самой или передать большой модели / долгой задаче / агенту;
- всё это видно и настраивается в наглядном приложении для Mac;
- позже — клиенты для Android, iOS, Windows.

Главное требование владельца: **не монолит**. Любую часть (обработчик фразы,
модель, коннектор, хранилище, синтез речи) можно добавить, заменить или
выкинуть, не трогая остальные.

## 2. Цели, не-цели, анти-цели

Цели:
- Колонка отвечает на русском голосом; первые звуки ответа — около 1.5 с
  после `utterance_end`, когда отвечает диспетчер. Это ориентир, а не условие
  приёмки этапа 1: ядро измеряет и пишет в журнал задержку каждого шага
  (STT, первая фраза модели, первый звук TTS), ускорение — по замерам.
- Несколько колонок: каждая со своим именем; если слово услышали две —
  отвечает одна.
- Обработчики фразы подключаются списком в настройках, работают параллельно,
  влияют только на промпт.
- Исполнители (модели, агенты) и связи «кто кому передаёт» настраиваются
  без правки кода.
- Возможности — только через MCP-коннекторы; ядро о конкретных возможностях
  не знает.
- Каждый человек — со своими заметками/делами (по голосу).
- Публичный API ядра, через который работают все клиенты, включая наш.
- Приложение для Mac в тёмном стиле «как нативное» (образец — PopkaStudio,
  утверждённый набросок — раздел 9).

Не-цели (пока):
- Доступ из-за пределов дома (позже — через VPN, не открывая порты).
- Нативные клиенты Android/iOS/Windows (закладываем API, не пишем).
- Свой русский wake word (отдельная задача прошивки).
- Звонок напоминаний на колонке (позже через уведомления MCP → ядро).

Анти-цели (провал, даже если «работает»):
- Новый обработчик/модель/коннектор требует правки ядра или других модулей.
- Интерфейс ходит в ядро мимо публичного API.
- Голос используется как пароль (замки, деньги, доступ к опасному).
- Агент с доступом ко всему Mac (только разрешённые папки).
- Тишина: человек не понимает, что происходит с его просьбой.

## 3. Ограничения

- Mac: M2 Ultra, 128 ГБ. Ollama установлена. Модели сейчас:
  `fredrezones55/Gemma-4-Uncensored-HauhauCS-Aggressive` (6.3 ГБ — диспетчер),
  `gpt-oss:120b` (65 ГБ — большая локальная), `deepseek-r1:8b`,
  `deepseek-v3.1:671b` (404 ГБ — **в 128 ГБ не помещается**, локально
  непригодна; «умный» уровень — `gpt-oss:120b` или удалённая модель).
- Системный Python 3.9 — мал для MCP SDK (нужен ≥3.10). Ядро ставит свой
  Python через `uv` (есть в `/opt/homebrew/bin/uv`).
- Есть `node`/`npm`, `swift`/`xcodebuild`, macOS 15.3.
- Arduino IDE компилирует только корень скетча и `src/` — новые папки
  репозитория прошивке не мешают. (Позже прошивка переехала в `firmware/SmartEsp/`:
  IDE просматривает всю папку скетча и спотыкается о `core/.venv`.)
- Колонки говорят по протоколу из дизайна прошивки (раздел 7): PCM 16 кГц
  s16le моно, JSON-события с `turn`. Звук приходит уже очищенный (AEC + NS
  в ESP-SR).
- Всё работает в домашней сети; данные не уходят наружу, кроме случаев, когда
  владелец сам выбрал удалённого исполнителя.

## 4. Рассмотренные подходы

| | Подход | Плюсы | Минусы |
|---|---|---|---|
| **A** ✓ | Ядро на Python + веб-интерфейс в тонкой Mac-обёртке (Swift + WKWebView) | Всё нужное (Whisper, узнавание голоса, Piper, MCP, Ollama) есть на Python; интерфейс открывается с любого компьютера сети; ядро проверяется автотестами | Два языка (Python + TypeScript) и крошечная обёртка на Swift |
| B | Всё на Swift (SwiftUI, WhisperKit, MCP Swift SDK) | Полностью нативно, один язык | Узнавание голоса/шёпота придётся портировать; интерфейс только на Mac; каждый обработчик дороже |
| C | Ядро на Python + интерфейс на SwiftUI | Нативный интерфейс + Python-библиотеки | Два больших языка; интерфейс только на Mac; схема с перетаскиванием на SwiftUI заметно дороже |

Выбран **A** владельцем: расширяемость живёт в мире Python, вид как у
нативного приложения веб даёт без потерь (PopkaStudio — веб в обёртке).
Electron не берём — тяжёлый; обёртка на Swift на ~сотню строк.

Внутри ядра рассматривали: Home Assistant в центре — отказались (схема сети
моделей упирается в рамки HA, прошивку пришлось бы переделать под его
протокол). HA можно подключить позже как один MCP-коннектор для лампочек.

## 5. Как это работает

```
 колонки (ESP) ──/device WS──┐
 (позже телефон как колонка) │
                             ▼
                ┌──────────────────────── ядро (Python) ────────────────────────┐
                │ devices → STT → [обработчики ∥] → разговор → исполнители → TTS │──→ колонка
                │                                       ↕ MCP-хаб               │
                │ people · tasks · notify · config · api                         │
                └───────────────▲──────────────────────────────▲─────────────────┘
                                │ /api/v1 (HTTP + WS)          │ stdio (MCP)
            Mac-приложение / браузер / будущие клиенты    коннекторы (отдельные процессы):
                                                           заметки, лампочки, напоминания…
```

Путь одной фразы:
1. Колонка шлёт `wake` → модуль `devices` ждёт до 300 мс другие `wake` (арбитраж,
   раздел 7.2) → выбранная колонка пишет вопрос, остальным — `cancel_turn`.
2. Звук вопроса копится до `utterance_end` → **фраза** (`Utterance`): звук,
   колонка, время.
3. STT превращает звук в текст → фраза дополняется текстом.
4. Все включённые **обработчики** параллельно получают фразу и возвращают
   **пометки** (строки для промпта). Таймаут обработчика (по умолчанию 300 мс)
   или ошибка → его пометки нет, запись в журнал.
5. **Разговор** собирает промпт: системное описание исполнителя + пометки +
   история диалога с этой колонкой + текст. Отдаёт **диспетчеру**.
6. Диспетчер отвечает потоком. У него есть инструменты: инструменты всех
   подключённых коннекторов и `delegate(executor, task)`. При передаче он
   сначала говорит фразу («спрошу большую модель»), и она сразу звучит.
7. Текст ответа режется на предложения; каждое предложение сразу уходит в
   TTS со **стилем**, выбранным моделью (раздел 6.6), и звук — в колонку
   (`reply_start` → PCM → `reply_end`), не дальше ~10 с впереди
   воспроизведения.
8. Всё, что произошло, публикуется в ленту событий (`/api/v1/events`) —
   отсюда лента и подсветка пути в интерфейсе.

## 6. Устройство ядра

### 6.1 Правила (аналог `CLAUDE.md` прошивки)

Это правила, ради которых затевается дизайн. Они переносятся в
`core/CLAUDE.md` и проверяются на ревью.

- **Модуль** — папка-пакет `core/smartesp/<module>/`. Публичное — только то,
  что экспортирует его `__init__.py`. Остальное — внутреннее.
- **Модули не импортируют друг друга.** Общие типы и договоры (протоколы
  Python, `typing.Protocol`) — только в `core/smartesp/contracts/`: там нет
  логики, только dataclass'ы и протоколы (аналог `Types.h`).
- **Связка — `core/smartesp/main.py`** (аналог `SmartEsp.ino`): создаёт модули
  по конфигурации, соединяет их. Своей логики в нём нет. Единственное место,
  где видно, кто с кем работает.
- **Сменные части — за договором и в реестре.** STT, TTS, обработчик,
  исполнитель, хранилище — это реализации протокола из `contracts`, которые
  регистрируются под именем (`"whisper"`, `"piper"`, `"ollama"`). Конфигурация
  выбирает реализацию по имени. Добавить новую = новый файл + одна строка
  регистрации; остальной код не меняется.
- **Возможности — только через MCP.** В ядре нет кода про лампочки, заметки,
  напоминания и т. п.
- **Размеры:** файл ≤ 300 строк, функция ≤ 50 строк, модуль ≤ ~1000 строк.
  Вырос — делим. Цикломатическая сложность функции ≤ 10 (`ruff` C901).
- **Типы строгие:** `pyright` в режиме strict для `contracts/` и публичных
  интерфейсов модулей.
- **Async везде:** ядро — один процесс `asyncio`. Тяжёлое (STT, TTS,
  узнавание голоса) — в пуле потоков/процессов, чтобы не блокировать цикл.
- **Тесты без железа и моделей:** у каждого договора есть поддельная
  реализация (`fakes/`), каждый модуль тестируется с подделками (`pytest`).
  Плюс сквозной тест: поддельная колонка (Python-клиент `/device`) → ядро с
  подделками → ожидаемый звук ответа.
- **Зависимости зафиксированы** (`uv.lock`), новая библиотека — в том же PR.
- **Оформление:** имена на английском, комментарии и docstring'и на русском.
  `ruff format` + `ruff check`.
- **Git** — как для прошивки: ветка + PR, описание на русском
  (Что / Зачем / Как проверить).

### 6.2 Структура репозитория

```
SmartEsp/

  CLAUDE.md               ← общие правила + ссылки на правила частей
  core/                   ← ядро (uv-проект, Python 3.12)
    CLAUDE.md             ← правила раздела 6.1
    pyproject.toml, uv.lock
    smartesp/

    tests/  fakes/
```

Правила прошивки в корневом `CLAUDE.md` становятся разделом «Прошивка»;
у `core/`, `ui/`, `app/` — свои `CLAUDE.md`.

### 6.3 Модули ядра

| Модуль | Что делает | Договор (в `contracts`) |
|---|---|---|
| `devices` | Протокол `/device`, сессии колонок, имена, арбитраж, отправка ответа с темпом | выдаёт `Utterance`, принимает `ReplyAudio` |
| `stt` | Звук → текст | `SpeechToText.transcribe(pcm) -> str` |
| `stages` | Запускает включённые обработчики параллельно с таймаутом | `Stage.analyze(utterance) -> list[Annotation]` |
| `conversation` | Порядок хода: STT → обработчики → диспетчер → TTS → колонка; история диалога | — (оркестратор, знает только договоры) |
| `executors` | Исполнители: модель Ollama, (позже) удалённая модель, агент, фоновая задача; `delegate` | `Executor.run(request) -> AsyncIterator[ReplyPart]` |
| `tts` | Текст + стиль → звук | `TextToSpeech.styles()`, `.synthesize(text, style) -> AsyncIterator[pcm]` |
| `tools` | MCP-хаб: запускает коннекторы, собирает инструменты, вызывает их | `ToolHub.list_tools()`, `.call(name, args, person)` |
| `people` | Люди и образцы голоса | этап 4 |
| `tasks` | Фоновые задачи: статус, хозяин, остановка | этап 5 |
| `notify` | Доставка: лента, колонка (с часами тишины), MCP | этап 5 |
| `config` | Чтение/запись конфигурации, проверка схемы, события «изменилось» | `Config` |
| `api` | HTTP + WS API для клиентов | — |

Оркестратор `conversation` — единственный, кто знает порядок шагов, как
`session` в прошивке. Остальные модули о нём не знают.

### 6.4 Обработчики фразы (`stages`)

- `Utterance`: `pcm`, `device`, `started_at`, `text` (после STT).
- `Annotation`: `text` (строка для промпта, напр. «Говорит Даня, уверенность
  0.92»), `source` (имя обработчика), `data` (dict для интерфейса).
- Все включённые обработчики получают одну и ту же фразу, работают
  параллельно, не видят пометок друг друга. Порядок не важен.
- Обработчик не знает ни про модели, ни про TTS, ни про другие обработчики.
- Первые обработчики: `whisper_detect` (шёпот, этап 2), `speaker_id`
  (кто говорит, этап 4).

### 6.5 Исполнители и диспетчер (`executors`)

- Исполнитель в конфигурации: `id`, `name`, `kind` (`ollama`, позже
  `remote_api`, `agent`, `background`), `model`, `description` (для
  диспетчера: «вопросы на знания»), `system_prompt`, `can_delegate_to` (список
  id), `tools` (все MCP / выбранные / никакие).
- Диспетчер — обычный исполнитель, отмеченный как первый (`entry: true`).
- `delegate(executor, task)` — инструмент, который ядро даёт исполнителю,
  если у него непустой `can_delegate_to`; в описании инструмента — список
  исполнителей с их `description`. Это и есть «жонглирование»: поменяли
  описание или связь в интерфейсе → изменилась маршрутизация.
- Правило «без тишины»: системный промпт диспетчера требует перед
  `delegate` сказать короткую фразу; если модель не сказала, ядро
  проигрывает тон `thinking`.
- Делегирование максимум на 2 уровня (защита от циклов).

### 6.6 Голос ответа и стиль (`tts`)

- TTS публикует список стилей: этап 1 — `normal`, этап 2 — `quiet`.
- Модель выбирает стиль сама: ответ начинается служебной меткой, напр.
  `[style:quiet]`, которую `conversation` вырезает (или инструмент
  `set_style` — решит исполнитель плана по надёжности на gemma). Нет метки —
  `normal`.
- `quiet` в первой версии: тот же голос Piper, громкость отсчётов ×0.35,
  чуть медленнее. Громкость колонки (`volume`) не трогаем.
- Реализация этапа 1: Piper, русский голос (напр. `ru_RU-irina-medium`),
  выход ресемплируется в 16 кГц моно.

### 6.7 Коннекторы (`tools`, этап 3)

- Коннектор — отдельный процесс MCP (stdio), запускается ядром по
  конфигурации (`command`, `args`, `env`, вкл/выкл).
- Ядро при старте коннектора запрашивает список инструментов и отдаёт их
  исполнителям. Нет нужного инструмента — модель говорит, что сделать
  некуда (это в системном промпте).
- Человек передаётся в `_meta.person` каждого вызова. Наши коннекторы его
  используют; чужие — игнорируют.
- Первый свой коннектор — `connectors/notes_files/`: заметки как
  Markdown-файлы, папка на человека (`<data>/people/<id>/notes/`). Внутри —
  договор хранилища (`save/find/delete`), чтобы позже добавить git/облако.

### 6.8 API для клиентов (`api`)

- `/device` — WebSocket колонок (протокол v2, раздел 7). Любое устройство,
  говорящее по нему (в будущем телефон), — колонка.
- `/api/v1/…` — HTTP JSON: конфигурация (колонки, люди, обработчики,
  исполнители, коннекторы), задачи, история. Схема OpenAPI генерируется
  автоматически — из неё потом генерируются клиенты для мобильных/Windows.
- `/api/v1/events` — WebSocket ленты событий: фраза, пометки, кто ответил,
  путь, тайминги, задачи, состояние колонок.
- Веб-интерфейс пользуется только этим API — никаких скрытых путей.
- Доступ: токен в заголовке. Токен создаётся при первом запуске и лежит в
  `<data>/token`; Mac-обёртка подставляет его сама, для других устройств он
  показывается в интерфейсе. `/device` в этапе 1 без токена (домашняя сеть).

### 6.9 Данные и конфигурация

- Папка данных по умолчанию `~/SmartEsp/`: `config.yaml`, `people/`, `logs/`,
  `token`. Путь меняется переменной окружения.
- `config.yaml` — единственный источник настроек; интерфейс меняет его через
  API; ядро применяет изменения без перезапуска, где возможно.

## 7. Протокол колонок v2 (изменения прошивки)

Совместим с v1 по звуку и ходам. Изменения:

### 7.1 Сообщения

| Направление | `type` | Изменение |
|---|---|---|
| ESP → ядро | `hello` | + `device_id` (MAC Wi-Fi, строка), + `protocol: 2` |
| ESP → ядро | `wake` | + `level` — громкость слова (напр. средний уровень сигнала за слово от AFE, 0..1 или дБ) для арбитража |
| ядро → ESP | `cancel_turn` (новое) | `turn`. ESP молча прекращает ход **в любом состоянии**: перестаёт слать звук, обрывает воспроизведение, не шлёт `utterance_end`/`playback_done`, возвращается к ожиданию слова |
| ядро → ESP | `announce` (новое) | `turn` — номер, выданный ядром. Ядро само начинает ответ, когда колонка ждёт слово: ESP переходит в `Speaking` для этого хода, дальше как обычно `reply_start` → звук → `reply_end` → `playback_done`. Если колонка занята — ядро ждёт и повторяет позже |
| ядро → ESP | `tone{name:"thinking"}` | уже есть; теперь ещё и **продлевает ожидание ответа** в `Waiting`/`Speaking` (сброс таймаута 15 с) |

Номера ходов: ESP считает свои с 1 вверх; ядро для `announce` берёт номера
с установленным старшим битом (`0x80000000 | n`), чтобы они не пересекались.

Имя колонки хранится в ядре по `device_id`, в прошивке его нет.
Колонка без `device_id` (прошивка v1) принимается, но в арбитраже не
участвует и `announce` не получает.

### 7.2 Арбитраж

- Первый `wake` открывает окно 300 мс. Все `wake` в окне — кандидаты.
- Победитель — с наибольшим `level`; остальным — `cancel_turn`.
- Звук победителя, пришедший за время окна, не теряется (буферизуется).
- Тон `wake` колонки играют сами и сразу, поэтому при двух услышавших
  пикнут обе — принимаем ради отсутствия задержки.
- **Опоздавший `wake`:** `wake` другой колонки в течение 1.5 с после
  решённого окна считается тем же словом → `cancel_turn`.
- **Новое слово на другой колонке, пока первая занята** (ждёт или говорит
  ответ): новый ход побеждает, первой — `cancel_turn` (она замолкает).
  Человек перешёл в другую комнату или перебил — отвечаем там, где спросили.

### 7.3 Долгие ответы и речь по инициативе ядра

- Передача задачи с ответом в пределах разговора (большая модель):
  ход остаётся открытым; диспетчер сразу говорит фразу («спрошу большую
  модель»), затем ядро шлёт `tone thinking` каждые ~5 с, пока не придёт
  ответ (и таймаут колонки не истекает). Предел — 60 с, дальше ядро
  говорит «долго думает, сообщу, когда будет готово» и переводит задачу в
  фоновую.
- Фоновые задачи, агенты, уведомления (этап 5) говорят через `announce`.
  Протокол закладывается сразу в v2, чтобы не менять прошивку второй раз.

### 7.4 Что меняется в прошивке

`hello` с `device_id` (server_link), `level` в событии слова
(voice_frontend → Types.h → session), команды `cancel_turn` (в любом
состоянии: `StopCapture`/`StopPlayback`, `SetActiveTurn(0)`, `Idle`, без
тона) и `announce` (из `Idle`: `SetActiveTurn(turn)`, `Speaking`, ждать
`reply_start`), продление таймаута по `tone thinking`. Отдельный PR прошивки
по её правилам, с тестами `Session` и `Protocol`.

## 8. Этапы (каждый — свой план и серия PR)

1. **Голосовой цикл.** Каркас `core/` по правилам 6.1, `contracts`, `config`,

   Готово, когда: вопрос голосом → ответ голосом на плате; арбитраж двух

## 9. Интерфейс (утверждённый набросок)

Тёмный холст в точку, плавающие скруглённые панели (образец — PopkaStudio):
- слева: разделы списками — колонки, люди, обработчики, исполнители,
  коннекторы, фоновые задачи;
- центр: схема колонки → обработчики → диспетчер → исполнители, снизу
  коннекторы; неподключённое — пунктиром; путь последней фразы подсвечен;

- справа: настройки выбранного блока (для исполнителя: модель, где работает,
  кому может передать, описание для модели);
- снизу: лента фраз с пометками и путём; клик — подсветка пути на схеме;
- сверху: Схема / Лента / Задачи, масштаб; справа — состояние Ollama и колонок.

Набросок: `.superpowers/brainstorm/…/content/home-dark.html` (не в git).

## 10. Решения, принятые без обсуждения (проверить)

- Python 3.12 через `uv`; `asyncio`; веб-сервер — FastAPI + uvicorn.
- STT — Whisper на Apple Silicon (`mlx-whisper`, модель large-v3-turbo);
  если не укладывается в задержку — `faster-whisper` или модель меньше.
- TTS — Piper, голос `ru_RU-irina-medium` (можно сменить).
- `quiet` — уменьшение громкости отсчётов, а не команда `volume` колонке
  (раньше в разговоре предлагалось через `volume`; так проще — громкость
  колонки не надо восстанавливать).
- Модель выбирает стиль меткой в начале ответа.
- `deepseek-v3.1:671b` локально не используем (не помещается в память).
- Интерфейс — TypeScript + React + Vite, схема — React Flow (`@xyflow/react`).
- Mac-обёртка — Swift + WKWebView + значок в строке меню, без Electron.
- Папка данных `~/SmartEsp/`, токен для `/api`, `/device` без токена.
- Арбитраж: окно 300 мс, победитель по `level`; пикают обе колонки;
  опоздавший `wake` в течение 1.5 с — то же слово; новое слово на другой
  колонке отменяет ход на первой.
- История диалога — общая на дом (последние ~10 ходов или 5 минут), чтобы
  «а завтра?» работало и с другой колонки; после этапа 4 — на человека.
- Задержка 1.5 с — ориентир с момента `utterance_end`, не условие приёмки.
- Долгая передача — ход открыт, `thinking` каждые 5 с, предел 60 с, дальше
  фоновая задача; речь по инициативе ядра (`announce`) — сразу в протоколе v2.
- Номера ходов ядра — со старшим битом.
- Ограничения размера: файл 300 / функция 50 / модуль ~1000 строк.
