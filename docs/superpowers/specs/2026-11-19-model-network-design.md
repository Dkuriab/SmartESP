# Сеть моделей: передача задачи другой модели

Статус: черновик, ждёт утверждения владельцем. Дополнение к
`2026-11-18-core-design.md`: разделы 1, 5 (шаг 6), 6.5, 7.3 и 8 («этап 2: `delegate`
и несколько исполнителей»).

## 1. Зачем

Диспетчер (быстрая gemma, ~0,3 с до первого звука) хорошо отвечает на простое,
но на вопросы, где надо подумать, знать или посчитать, его не хватает. Владелец
хочет сеть: маленькая модель отвечает сразу и сама решает, ответить или передать
задачу модели посильнее. При передаче она сначала говорит, что передала, —
«чтобы не было тишины и было понятно, что происходит». Кто кому может передавать
и как описан каждый исполнитель — видно и меняется в приложении.

## 2. Цели, не-цели, анти-цели

**Цели**
- Диспетчер получает инструмент `delegate(executor, task)`.
  - Сначала он говорит короткую фразу, она сразу звучит.
  - Потом вызывает инструмент.
  - Ядро отдаёт задачу выбранному исполнителю, и его ответ звучит в той же
    колонке, в том же ходе.
- Пока исполнитель думает, колонка подаёт «думаю». Тишины нет.
- Исполнителей может быть сколько угодно. У каждого есть модель, описание
  («что это за исполнитель»), свой промпт и связи «кому могу передать».
- **У каждой связи своё условие** «в каких случаях вызывать» — текст
  владельца. Например:
  - диспетчер → big: «сложные вопросы, расчёты, подробные объяснения»;
  - диспетчер → другая модель: «вопросы про код».

  Условие связи — главное, по чему модель решает, кому передать.
- В приложении:
  - все исполнители видны на схеме, связи «кто кому передаёт» показаны
    стрелками;
  - путь хода подсвечивается до исполнителя, который ответил;
  - в ленте видно «→ Большая модель»;
  - исполнителей можно добавлять, удалять и настраивать, всё применяется на
    лету.

**Не-цели (эта версия)**
- Долгие фоновые задачи («следи за ценой 5 часов»), агенты в папках, удалённые
  модели — этап 5. Если передача не уложилась в предел, колонка честно говорит,
  что не успела, и ход заканчивается. В фон ничего не уходит.
- Инструменты подключаемых возможностей (MCP) — этап 3. Механизм инструментов
  делаем так, чтобы туда добавились и они.
- Связи, которые тянутся мышкой на схеме. Связи задаются флажками в настройках
  исполнителя.
- Скачивание моделей. Модель для «большого» исполнителя на этом Mac —
  `deepseek-r1:8b`. Владелец поменяет её в приложении.

**Анти-цели**
- Тишина: задача ушла, а колонка молчит и не подаёт «думаю».
- Цикл передач (A → B → A …) или бесконечное ожидание.
- Сеть зашита в код: новый исполнитель требует правки кода.
- Звучащий ответ обрывается из-за смены настроек исполнителей.

## 3. Ограничения

- Ollama 0.40.8.
  - `gpt-oss:120b` не загружается: старый файл модели.
  - `deepseek-r1:8b` работает.
  - gemma поддерживает инструменты (capabilities: tools).
- Spike 2 от 2026-11-19: две цели с разными условиями («Большая модель» —
  рассуждения и расчёты, «Программист» — код), правило из 5.2, 18 прогонов.
  - **Верно 16:** простые сам, сложные — big, код — coder.
  - **Ошибка 2:** на «почему в JavaScript 0 == ''» модель сказала «Сейчас
    спрошу большую модель», но инструмент не вызвала.

  Отсюда страховка в 5.3, п. 7а. Первые варианты правила давали 13/18:
  - с общим примером «спрошу большую модель» код уходил big;
  - с id в примере модель произносила «спрошу big» и отвечала сама.
- Spike 1 от 2026-11-19 (gemma, одна цель, 24 прогона):
  - сложные вопросы (физика, расчёт, пересказ романа, сравнение, план,
    история) — 12/12 «Сейчас спрошу большую модель.» + `delegate`;
  - текст идёт до вызова инструмента и приходит через 0,04–0,3 с;
  - простые («привет», «спасибо», «как тебя зовут») — 12/12 отвечает сам,
    без инструмента.
- Spike 5 (живая проверка, gemma, одна цель): шаблонная фраза «Сейчас спрошу <имя исполнителя>.» —
  модель говорит id («Сейчас спрошу big.») и не вызывает инструмент (10/20); нейтральный пример
  «Минутку, сейчас узнаю» — 20/20 (T=0,2), 19/20 (T=1,0); две цели 24–27/28; простые не передаёт.
- Правила ядра (`core/CLAUDE.md`): модули импортируют только `contracts`,
  `main.py` и `wiring.py` — без логики, реестры по имени, файлы ≤ 300 строк.
- Договор ленты событий и API (план «ядро для приложения») расширяется только
  новыми полями.

## 4. Подходы (выбран в разговоре)

| | Подход | Почему |
|---|---|---|
| ✓ | **Инструмент `delegate` через вызов инструментов Ollama** | Тот же механизм нужен для MCP на этапе 3. gemma вызывает его надёжно (spike). |
| | Метка в тексте `[передать:…]` | Работает с любой моделью, но это костыль: для MCP всё равно нужны инструменты. |
| | Отдельный сортировщик до диспетчера | Добавляет задержку перед каждым ответом. |

## 5. Как устроено

### 5.1 Настройки исполнителя

`executors` — список, ровно один `entry: true`, как сейчас. Новые поля:
- `description: str` — что это за исполнитель («большая модель: рассуждения,
  расчёты, знания»).
- `delegates: list[{to: str, when: str}]` — связи «кому могу передать» с
  условием на каждой. `when` — «в каких случаях вызывать» этого исполнителя
  именно отсюда.
  - Пустой `when` — берётся описание цели.
  - Пусто и то и другое — связь неактивна: ядро её не предлагает модели.

**Проверка настроек:**
- id уникальны;
- цели существуют;
- исполнитель не передаёт сам себе;
- одна цель — не больше одной связи.

Неверно — ошибка с понятным текстом. В приложении это 422.

**По умолчанию — два исполнителя:**
- `dispatcher` — как сейчас, плюс связь
  `delegates: [{to: big, when: "сложные вопросы: рассуждения, расчёты,
  подробные объяснения, знания, которых может не быть у тебя"}]`;
- `big` — «Большая модель», `deepseek-r1:8b`:
  - описание «сложные вопросы: рассуждения, расчёты, подробные объяснения,
    знания»;
  - свой промпт: «Ты отвечаешь голосом через колонку: по-русски, без разметки
    и списков, связно, до 6–8 предложений».

Старые установки получают `big` сами: в `config.yaml` хранятся только изменения
владельца. Если владелец менял `executors`, его список остаётся как есть, без
`big`.

### 5.2 Инструмент и правило для модели

Ядро само строит для исполнителя с активными связями:
- **Инструмент `delegate`.** Параметр `executor` — enum из id активных целей.
  В описании инструмента — по строке на связь: «id — имя: вызывай, когда
  <when>». Параметр `task` — «задача своими словами, со всем нужным
  контекстом».
- **Правило в системном промпте.** Добавляется так же, как правила
  обработчиков, и перечисляет условия связей:
  > Ты можешь передать задачу другим исполнителям. Каждому — свои вопросы:
  > — Большая модель: <when>.
  > — Программист: <when>.
  >
  > Если вопрос относится к области одного из исполнителей, сначала скажи
  > одну короткую фразу (например «Минутку, сейчас узнаю»), затем вызови
  > инструмент delegate с этим исполнителем; без вызова delegate такую фразу
  > не говори. Если вопрос подходит под условие исполнителя, обязательно
  > передай его, даже если кажется, что можешь ответить сам. Если подходят
  > несколько, выбери того, чья область описывает вопрос точнее. Простые
  > вопросы и приветствия отвечай сам. Бытовые просьбы и действия (включить или
  > выключить, записать, поставить таймер, список, счёт) не передавай: делай их
  > своими инструментами, а если нужного инструмента нет — скажи, что нет доступа.

  (Хвост уточнён после живой проверки W8/W9: прежнее «бытовые просьбы отвечай
  сам, без инструмента» с коннекторами читалось как «без инструментов вообще»;
  «нет доступа» относится только к действиям и данным, не к разговору.)

  В параметре `executor` инструмента — тоже описание «id — имя: when» для
  каждой цели. Эта формулировка проверена в spike 2: две цели, 18 прогонов,
  16 верно (см. раздел 3).

Владелец правит описания, связи и их условия. Правило и инструмент ядро
собирает само. Итоговый промпт виден в приложении (`dispatcher_prompt` уже есть).

### 5.3 Ход с передачей

1. Диспетчер отвечает потоком. Текст до вызова инструмента — обычные куски
   ответа: режутся на предложения и сразу звучат.
2. Пришёл вызов `delegate(executor, task)`. Ядро:
   - запоминает путь;
   - получает отметку «передано X»: колонка подаёт «думаю» каждые 8 с, как
     сейчас при ожидании первого куска;
   - запускает исполнителя X с сообщениями:
     - свой системный промпт X;
     - история диалога;
     - вопрос человека;
     - строка «Задача от диспетчера: <task>».
3. Ответ X звучит в том же ходе тем же стилем: если диспетчер выбрал `quiet`,
   X тоже звучит тихо.
4. **Пределы:**
   - первый кусок от X — до **90 с** (`DELEGATE_FIRST_PART_LIMIT_S`), паузы
     между кусками — до 20 с, как сейчас;
   - не уложился — звучит «Не получилось ответить вовремя, спроси попозже», ход помечен
     ошибкой. Фраза вместо сигнала ошибки: сигнал уходит вместе с концом
     ответа и на колонке перебил бы фразу.
5. **Глубина — максимум 2 передачи** (диспетчер → A → B). У исполнителя на
   глубине 2 инструмента нет.
6. **X недоступен** (нет модели, Ollama упала) или ничего не сказал — звучит
   «<Имя> сейчас не отвечает.», ход помечен ошибкой. Фраза вместо сигнала
   ошибки.
7. **Диспетчер вызвал `delegate` без фразы** (в ходе ещё нет ничего, что
   можно озвучить; одна метка `[style:…]` не в счёт) — ядро говорит за него
   «Минутку, сейчас узнаю.» обычным куском текста до записи передачи. Фраза
   попадает в первый кусок ответа (после метки стиля, если она была, —
   `quiet` действует) и в историю как текст сообщения assistant с вызовом.
   Немедленного тона «думаю» нет (периодические, раз в 8 с, идут). В журнале —
   «вызов без фразы — говорим «Минутку…»». Не для передачи по фразе без вызова
   и не второй раз за ход (вложенный молчаливый вызов). Причина: вживую 2 из 3
   вызовов шли без фразы, 7–9 с колонка подавала только тоны.

   7а. **Фраза без вызова.** Ответ диспетчера закончился одним коротким
   предложением, в котором есть имя ровно одной активной цели («Сейчас спрошу
   большую модель.», «Спрошу программиста»), а инструмент не вызван. Тогда
   ядро само передаёт этой цели с задачей = вопрос человека.
   - Сравнение имён — без регистра, по основе слова: «программиста» находит
     «Программист».
   - Id цели, стоящий во фразе отдельным словом («Сейчас спрошу big.»), тоже
     считается названием: модель с одной целью иногда говорит id.
   - Совпало несколько целей или ни одной — ничего не делаем.
   - Если передача сделана так, в журнале и в `delegations` она помечена
     `auto: true`.
8. **Неизвестная цель или пустая задача в вызове** — передачи нет. Ход
   заканчивается тем, что уже сказано. Если не сказано ничего — сигналом
   ошибки. В журнале — предупреждение.
9. **История.** Ход с передачей хранится сообщениями: вопрос (user);
   assistant — фраза диспетчера до передачи с вызовом `delegate{executor, task}`;
   tool (`tool_name="delegate"`) — всё, что сказали цели (вложенные тоже,
   через пробел). Ход без передачи — пара user/assistant. Одной плоской репликой
   «фраза + ответ» хранить нельзя: gemma перенимает ответ без вызова
   (2/9 против 9/9 со структурой). Пределы истории считают ходы, не сообщения.
   Цели получают диалог без структуры вызовов: tool-сообщения становятся
   ответами assistant, соседние ответы склеиваются. Входной исполнитель без
   целей получает такой же плоский диалог.
10. **Режим размышлений** (`think`) у X выключен, как у диспетчера: на голосе
    рассуждения не нужны.

### 5.4 Где живёт код

**Договоры (`contracts/executor.py`):**
- `ChatMessage` получает `tool_calls: tuple[ToolCall, ...] = ()` и
  `tool_name: str = ""`; роль `tool` (результат вызова). Константа
  `DELEGATE_TOOL = "delegate"` лежит здесь же: модули импортируют только
  `contracts`.
- `ReplyPart` получает необязательные поля, текст остаётся:
  - `tool_call: ToolCall | None`;
  - `handoff: str | None` — id исполнителя, которому передано.
- `@dataclass ToolCall(name, arguments)`;
- `ToolSpec(name, description, parameters)`.
- `Executor.run(messages, tools: Sequence[ToolSpec] = ())` — инструменты
  необязательные.

**`executors/ollama_executor.py`** отдаёт `tools` в Ollama и превращает
`tool_calls` из потока в `ReplyPart(tool_call=…)`.

**Новый модуль `network/`** — «сеть исполнителей»:
- реализует тот же договор `Executor`, поэтому для оркестратора он просто
  исполнитель;
- получает словарь исполнителей по id (собирает `wiring` через реестр) и
  их описания и связи;
- строит инструмент и правило;
- перехватывает вызов `delegate`, отдаёт `ReplyPart(handoff=id)` и затем куски
  ответа X;
- держит глубину, ловит ошибки X и отдаёт готовую фразу об ошибке;
- импортирует только `contracts`.

**Оркестратор:**
- на `handoff` записывает путь;
- переключает ожидание: «думаю» и предел 90 с для первого куска после
  передачи;
- `answer` копит только текст.

**Пульт и связка:**
- раздел `executors` (и `stages`) пересобирает всю сеть, как сейчас
  пересобирает входного исполнителя;
- `release` выгружает модели, которые больше не используются ни одним
  исполнителем.

### 5.5 Лента событий и API

Только новые поля, старые не меняются:
- в `turn_finished`:
  - `path: list[str]` — id исполнителей по порядку, например
    `["dispatcher", "big"]`;
  - `delegations: list[{from, to, task}]`;
- в `TurnOut` — те же поля;
- `dispatcher_prompt` в `GET /config` уже показывает итоговый промпт, теперь
  с правилом передачи.

### 5.6 Интерфейс

**Схема.**
- Вместо одного узла «Диспетчер» — колонка «Исполнители»: входной наверху,
  остальные под ним.
- Стрелки — по `delegates`. На стрелке — короткая подпись условия `when`
  (обрезается с многоточием, полный текст во всплывающей подсказке).
  Неактивная связь — пунктиром.
- Голос получает связи от всех исполнителей.
- Путь хода подсвечивается по `path`: колонка → обработчики → диспетчер → big
  → голос.

**Лента.** У хода с передачей — метка «→ <имя>». В карточке хода — задача,
которую передал диспетчер.

**Левая панель.** Раздел «Исполнители» со списком и кнопкой «Добавить».

**Настройки исполнителя:**
- имя;
- модель (список из Ollama);
- описание «Когда ко мне обращаться»;
- промпт;
- «Может передавать:» — строка на каждого другого исполнителя:
  - флажок;
  - поле «Когда вызывать» (подсказка-заглушка — описание цели);
- «Удалить» (не для входного; удаление убирает и ссылки на него у других).

Нынешняя панель диспетчера становится частным случаем этой панели. Итоговый
промпт показывается только у входного.

Новый исполнитель создаётся с id `executor-N`, моделью диспетчера и пустым
описанием. Связь на него с пустыми «Когда вызывать» и описанием сохраняется,
но помечена «неактивна — укажите, когда вызывать».

## 6. Проверка

**Ядро (подделки):**
- поток диспетчера «фраза + вызов» — фраза звучит, затем ответ X, `path`,
  `delegations`;
- «думаю» во время ожидания X; предел 90 с → фраза вместо сигнала ошибки;
- X падает → «<Имя> сейчас не отвечает.»;
- глубина 2;
- вызов без фразы → звучит «Минутку, сейчас узнаю.», она же в истории; тона
  «думаю» сразу нет; только метка стиля — фраза после неё; передача по фразе
  без вызова и второй вложенный вызов — без своей фразы; цель сразу
  недоступна → «Минутку… <Имя> сейчас не отвечает.», ход — ошибка, не в
  истории;
- неизвестная цель;
- стиль `quiet` переходит к X;
- история: передача хранится как вызов `delegate` и ответ `tool`; вложенные — одна пара;
  цели получают плоский диалог;
- смена настроек исполнителей во время передачи — ход договаривает старой
  сетью;
- проверка настроек:
  - цикл ссылок допустим, глубину держит ядро;
  - ссылки на себя, несуществующие цели и повторные связи — ошибка;
- условия связей попадают в инструмент и правило; пустой `when` даёт
  описание цели; пустые оба — связь не предлагается;
- с моделями: две цели с разными условиями («вопросы про код» и «история и
  литература») — gemma выбирает нужную.

**Ollama-исполнитель:** разбор `tool_calls` из потока (объект и словарь),
передача `tools`.

**С моделями (`@pytest.mark.models`)** — правило и инструмент на gemma:
- 6 сложных вопросов → `delegate`;
- 6 простых → без него.

**Вживую:**
1. сложный вопрос (WAV, озвученный нашим TTS) через `tools/fake_device.py` →
   фраза диспетчера, «думаю», ответ deepseek;
2. в журнале и ленте `path`;
3. в интерфейсе подсветка до «Большой модели».

**Интерфейс:** тесты схемы (узлы исполнителей, стрелки, подсветка по `path`),
настроек исполнителя (флажки, удаление, описание-пустое) и ленты (метка
передачи).

## 6а. Ответы на вопросы проверяющего (решения исполнителя дизайна)

1. **Прогрев моделей исполнителей, кроме входного.**
   - Модели прогреваются в фоне при старте и после смены настроек и никогда
     не блокируют ни старт, ни применение изменения.
   - Не прогрелась (нет модели) — запись в журнале и в состоянии исполнителя
     для интерфейса («модель недоступна»). Передача ей даёт фразу «<Имя>
     сейчас не отвечает.»
   - Входной исполнитель — как сейчас: при смене настроек должен прогреться.
   - `keep_alive` — своё у каждого исполнителя, по умолчанию 24h. Памяти
     128 ГБ хватает на gemma и deepseek вместе.
   - Ожидание выгрузки старой модели (`TURN_WAIT_S`) не меньше предела
     передачи плюс запас: 150 с.
2. **Модель без поддержки инструментов** (по `capabilities` из
   `ollama show`).
   - Изменение принимается. Исполнитель с такой моделью работает без
     инструмента и без правила передачи.
   - Интерфейс показывает у него «эта модель не умеет передавать задачи».
   - Связи из него — пунктиром, «неактивна».
3. **Промпт исполнителя, кроме входного.**
   - Он получает свой промпт, правила обработчиков (как входной) и, если у
     него есть связи, своё правило передачи. Так метка `[style:quiet]` и
     пометки обработчиков понятны и ему.
   - Метка стиля в начале его ответа учитывается, если стиль ещё не выбран
     фразой диспетчера.
   - В `GET /config` появляется `executor_prompts: {id: итоговый промпт}`.
     `dispatcher_prompt` остаётся. Интерфейс показывает итоговый промпт у
     каждого исполнителя.
4. **Мелкие решения:**
   - второй `delegate` в одном ответе игнорируется (запись в журнал);
   - перебивание (barge-in) отменяет и X;
   - у хода без передачи `path = [id входного]`;
   - пустая связь (без `when` и без описания) молча не предлагается, это не
     ошибка проверки;
   - повторная цель в одном списке — ошибка проверки.

## 7. Решения, принятые без обсуждения (проверить)

- **«Большая модель» по умолчанию** — `deepseek-r1:8b`, id `big`.
- **Предел ожидания** первого куска после передачи — 90 с, затем «не успела».
  В фон не переводим до этапа 5.
- **Фразы ошибок:**
  - «Не получилось ответить вовремя, спроси попозже»;
  - «<Имя> сейчас не отвечает.»
- **Правило передачи** — текст из spike, ядро собирает его само. Владелец
  меняет описания, а не правило.
- **Связи** — флажками в настройках, не мышкой на схеме.
- **X получает всю историю и вопрос**, а не только задачу диспетчера: так он
  не теряет контекст «а завтра?».
- **Условия — на связи** (желание владельца). Описание исполнителя служит
  запасным условием для связи с пустым `when`.
