# SmartESP — дизайн прошивки умной колонки

Дата: 2026-11-15. Статус: на ревью.

## 1. Зачем

SmartESP — умная колонка на ESP32-S3. Она ждёт слово-активатор, слушает
вопрос, отправляет его на сервер с нейросетью и проигрывает ответ.
Слово-активатор работает и во время ответа, так что ответ можно перебить.

Сервер (распознавание речи, нейросеть, синтез ответа) пока живёт на ноутбуке
в локальной сети. Нейросеть может быть локальной или удалённой — это решает
сервер, прошивка от этого не зависит.

Этот документ описывает **только прошивку ESP32** и протокол связи с сервером.
Сервер — отдельный проект, обсуждается после прошивки.

## 2. Цели, не-цели, анти-цели

**Цели**
- Слово-активатор распознаётся на самой ESP, в том числе во время
  воспроизведения ответа (эхоподавление).
- Минимальная задержка от конца фразы до начала ответа: всё потоком.
- Связь с сервером по WebSocket: звук в обе стороны + команды от сервера.
- Код разбит на независимые модули по правилам `CLAUDE.md`, каждый читается
  и ревьюится отдельно.

**Не-цели (сейчас не делаем)**
- Сервер с нейросетью (отдельный проект). В этом проекте — только простой
  тестовый сервер-эхо для проверки протокола.
- Своё слово-активатор (в т. ч. русское). Используем «Hi, ESP» из ядра.
- Сжатие звука, шифрование (`wss://`), обновление по воздуху (OTA),
  настройка Wi-Fi через телефон/веб-страницу, несколько устройств.
- Голосовые команды на самой ESP (MultiNet).

**Анти-цели (провал, даже если «работает»)**
- Звук с микрофона уходит с устройства до слова-активатора.
- Модули знают друг о друге или делят глобальные переменные.
- Пропуски/щелчки звука из-за того, что кто-то заблокировал `loop()`.

## 3. Ограничения

**Железо** (проверено пробной прошивкой):

| Устройство | Пин | GPIO |
|---|---|---|
| Микрофон INMP441 (L/R → GND, левый канал) | SCK / WS / SD | 5 / 4 / 9 |
| Усилитель MAX98357A | BCLK / LRC / DIN | 7 / 6 / 8 |

Модуль ESP32-S3-WROOM **N16R8**: 16 МБ флеша, 8 МБ PSRAM (OPI).

**Сборка** (Arduino IDE, Tools):

| Пункт | Значение |
|---|---|
| Ядро | esp32 by Espressif **3.3.12** |
| Board | ESP32S3 Dev Module |
| Flash Size | 16MB (128Mb) |
| Partition Scheme | ESP SR 16M (3MB APP/6MB SPIFFS/3.9MB MODEL) |
| PSRAM | OPI PSRAM |

**Особенности ESP-SR, выясненные пробной прошивкой** (`spikes/wakeword_aec`):
- Без PSRAM ESP-SR падает при старте (нет памяти под эхоподавление).
- Обёртка `ESP_SR` из ядра всегда загружает MultiNet, и на ядре 3.3.12 он
  падает в `build_fsts`. Кроме того, обёртка не отдаёт очищенный звук.
  **Поэтому работаем с обработчиком звука ESP-SR (AFE) напрямую.**
- Заголовок `ESP_SR.h` всё равно подключаем: только тогда ядро кладёт модели
  (`srmodels.bin`) в сборку и прошивает их.
- Формат входа AFE — `"MR"`: микрофон + образец того, что играет динамик.
  Эхоподавление с образцом работает заметно лучше, чем без него.
- Рабочие параметры: задержка образца **80 мс**, микрофон — 32-битный отсчёт
  сдвигается на **14** бит вправо.
- Встроенный в ядро WebSocket-клиент отсутствует → библиотека.

**Библиотеки** (точные версии — в README):
- `WebSockets` by Markus Sattler — **2.7.2**.
- `ArduinoJson` by Benoît Blanchon — последняя 7.x на момент PR, версия
  фиксируется в README.

## 4. Рассмотренные подходы

| Решение | Варианты | Выбрано | Почему |
|---|---|---|---|
| Где ловить слово | На ноутбуке (openWakeWord, любое слово, постоянный поток звука) / **на ESP (ESP-SR)** | ESP | Звук не уходит до слова, колонка не глохнет без постоянного потока; английское слово устраивает |
| Как вызывать ESP-SR | Обёртка `ESP_SR` / **AFE напрямую** | AFE | Обёртка падает на MultiNet и не отдаёт очищенный звук |
| Связь с сервером | **WebSocket** / HTTP-запросы / свой протокол на TCP/UDP | WebSocket | Потоком в обе стороны, сервер может прислать команду в любой момент; HTTP добавляет секунды задержки, свой протокол сложнее без выигрыша |
| Как модули общаются | **Связка в `SmartEsp.ino`** / события-подписки / общие глобальные | Связка в `.ino` | Весь поток данных виден в одном месте, модули проверяются по отдельности |
| Общие типы событий/команд | **Общий `src/common/Types.h`** / у каждого модуля свои типы, `.ino` переводит | Общий файл (выбор владельца) | Интерфейсы короче, `.ino` остаётся маршрутизацией без таблиц перевода |
| Формат звука | **PCM 16 кГц, 16 бит, моно** / сжатый (Opus и т. п.) | PCM | В локальной сети ~32 КБ/с — не проблема; без кодеков на ESP. Сжатие можно добавить позже внутри `server_link` |

## 5. Как работает колонка

**Сценарий**
1. **Ожидание.** ESP слушает слово. Звук никуда не уходит.
2. **«Hi, ESP».** Короткий сигнал. ESP шлёт на сервер **очищенный** звук.
3. **Конец фразы.** Определяет детектор речи ESP-SR (тишина ≥ 500 мс) **или**
   сервер командой `stop_listening` — что раньше. Передача звука прекращается.
4. **Ожидание ответа.** Сервер распознаёт, спрашивает нейросеть, синтезирует.
5. **Ответ.** Сервер шлёт звук, ESP начинает играть после ~100 мс накопленного
   звука. Слово-активатор продолжает работать.
6. **Перебивание.** «Hi, ESP» во время ответа (или ожидания) → ответ
   обрывается, ESP сообщает серверу `barge_in` → снова шаг 2.

**Состояния** (модуль `session`):

```
          wake                    конец фразы
  Idle ─────────▶ Listening ───────────────────▶ Waiting
   ▲                 ▲  │ таймаут 10 с              │ reply_start
   │                 │  ▼                           ▼
   │◀──── ошибка ────┼─ Idle                    Speaking
   │                 │                              │
   │                 └──────── wake (barge_in) ─────┤
   │◀───────────── воспроизведение закончилось ─────┘
```

- **Таймауты `Listening`** (решение исполнителя-дизайнера, можно поправить):
  - речь так и не началась за 5 с после слова → `utterance_end{reason:"no_speech"}`,
    переход в `Idle` (сервер ничего не отвечает);
  - вопрос длиннее 10 с от слова → `utterance_end{reason:"timeout"}`, переход
    в `Waiting` — сервер отвечает на то, что успел получить.
  На схеме выше «таймаут 10 с → Idle» читать как эти два случая.
- `Waiting` без ответа дольше 15 с → `Idle` + звук ошибки.
- Нет связи с сервером, а сказали слово → звук ошибки, остаёмся в `Idle`.
- «Hi, ESP» в `Listening` игнорируется; в `Waiting` и `Speaking` — перебивание.

## 6. Модули

Все модули — в `src/<module>/`, один класс, не подключают друг друга,
пины и настройки получают в `begin(...)`, не блокируют. Модули со звуком
работают в своих задачах FreeRTOS и обмениваются данными через внутренние
кольцевые буферы; наружу — неблокирующие `read`/`write`/`poll`.

**Общие типы** — в `src/common/Types.h`: только перечисления и простые
структуры, которыми модули обмениваются через `.ino` (`VoiceEvent`,
`ServerCommand`, `ClientEvent`, `Tone`, `Action` и т. п.). Без кода, функций
и переменных. Модули подключают этот файл, но не друг друга.

Ниже — интерфейсы в виде эскиза. Точные имена и типы — на усмотрение
исполнителя, смысл и разделение ответственности — нет.

### 6.1 `audio_out` — динамик

```cpp
struct AudioOutConfig { int bclkPin, lrcPin, dinPin; uint32_t refDelayMs = 80; };
bool begin(const AudioOutConfig&);
size_t write(const int16_t* pcm, size_t samples);  // в очередь; вернёт сколько принято
void playTone(Tone tone);       // Wake, Error, Thinking — встроенные короткие звуки
void stop();                    // очистить очередь, тишина сразу
void setVolume(float v);        // 0..1
bool isPlaying();
size_t readReference(int16_t* dst, size_t samples);  // образец для эхоподавления
```

- Своя задача пишет в I2S (стерео 16 бит, оба канала одинаковые — так
  проверено), каждый записанный кусок кладёт в буфер образца.
- При старте воспроизведения в образец добавляется `refDelayMs` тишины
  (выравнивание по задержке DMA — как в пробной прошивке).
- `readReference` возвращает нули, если играть нечего. Вызывается из задачи
  `audio_in`, поэтому потокобезопасен.
- Очередь воспроизведения — в PSRAM, **30 с** звука (~960 КБ). Сервер
  обязан не опережать воспроизведение больше чем на ~10 с (см. протокол).
  Если очередь всё же переполнилась — лишний звук отбрасывается, в Serial
  пишется предупреждение.

### 6.2 `audio_in` — микрофон

```cpp
struct AudioInConfig { int sckPin, wsPin, sdPin; int shift = 14; };
using ReferenceSource = std::function<size_t(int16_t* dst, size_t samples)>;
bool begin(const AudioInConfig&, ReferenceSource reference);
size_t read(int16_t* mic, int16_t* ref, size_t samples);  // пары «микрофон + образец»
int32_t takePeakLevel();  // пик с прошлого вызова — для отладки
```

**Почему образец берёт `audio_in`, а не `.ino`.** Эхоподавлению нужно, чтобы
образец совпадал по времени с микрофоном. Если брать образец в `loop()`,
рассинхрон будет «плавать» вместе с загрузкой `loop()` (Wi-Fi, сеть) и
эхоподавление развалится. Поэтому задача `audio_in` сразу после чтения
каждого кадра с микрофона вызывает `reference(...)` и кладёт пару в буфер —
ровно как в пробной прошивке. Функцию-источник передаёт `.ino`
(`[&](auto d, auto n){ return audioOut.readReference(d, n); }`), так что
модули друг о друге не знают, а связь видна в `.ino`.

### 6.3 `voice_frontend` — ESP-SR (AFE)

```cpp
struct VoiceFrontendConfig { uint32_t vadSilenceMs = 500; };
bool begin(const VoiceFrontendConfig&);
void feed(const int16_t* mic, const int16_t* ref, size_t samples);  // любыми кусками
bool pollEvent(VoiceEvent& ev);   // WakeWord, SpeechEnd
void setCapture(bool on);         // отдавать ли очищенный звук
size_t readClean(int16_t* dst, size_t maxSamples);  // очищенный звук, только при capture
```

- Внутри: `afe_config_init("MR", …, AFE_TYPE_SR, AFE_MODE_LOW_COST)`,
  `vad_min_noise_ms = vadSilenceMs`, MultiNet не загружается.
- `feed` копит куски до размера кадра AFE и подаёт в задачу подачи.
- Задача выборки (`fetch`) превращает результат в события и, если
  `capture` включён, кладёт очищенный звук в буфер.
- `SpeechEnd` выдаётся только при включённом `capture` (интересует только
  конец вопроса).

### 6.4 `wifi_link` — Wi-Fi

```cpp
bool begin(const char* ssid, const char* password);
void loop();         // переподключение с паузами через millis()
bool isConnected();
```

- `WiFi.setSleep(false)` — без энергосбережения, иначе провалы 100–300 мс.

### 6.5 `server_link` — WebSocket

```cpp
bool begin(const char* host, uint16_t port, const char* path, const char* fwVersion);
bool isConnected();
bool sendAudio(const int16_t* pcm, size_t samples);
bool sendEvent(const ClientEvent& ev);         // JSON, см. протокол
size_t readAudio(int16_t* dst, size_t maxSamples);  // принятый звук ответа
bool pollCommand(ServerCommand& cmd);          // принятые команды
```

- Сеть обслуживает своя задача FreeRTOS: подключение к недоступному хосту и
  отправка в мёртвое соединение могут висеть секунды, `loop()` от этого не
  останавливается. `sendAudio`/`sendEvent` только ставят в общую очередь
  (порядок звука и событий сохраняется), при переполнении — отбрасывают.
- Подключается, когда есть Wi-Fi; без Wi-Fi закрывает соединение явно.
  Пинг каждые 5 с: мёртвое соединение (сервер уснул) обнаруживается за ~11 с.
  При обрыве переподключается сам.
- После подключения шлёт `hello`.
- Ничего не знает о сценарии — только транспорт и разбор JSON.

### 6.6 `session` — сценарий (без железа)

```cpp
void begin(const SessionConfig&);  // таймауты
void loop();                       // таймауты через millis()
void onVoiceEvent(const VoiceEvent&);
void onServerCommand(const ServerCommand&);
void onConnection(bool connected);
void onPlaybackIdle();
bool pollAction(Action& a);        // что сделать: StartCapture, StopCapture,
                                   // SendEvent, StopPlayback, PlayTone, SetVolume
State state();
```

- Чистая логика: состояния из раздела 5. Модуль не трогает железо и сеть,
  только выдаёт «действия». Это дополнение к изначальному плану: без него
  логика сценария оказалась бы в `.ino`, что запрещено правилами.

### 6.7 `SmartEsp.ino` — связка

```
setup(): begin() всех модулей; audio_in получает audioOut.readReference.

loop():
  wifi.loop(); session.loop();          (server_link — в своей задаче)
  микрофон → фронтенд:   while (audioIn.read(mic, ref, N)) frontend.feed(mic, ref, n)
  события → сценарий:    while (frontend.pollEvent(e)) session.onVoiceEvent(e)
  вопрос → сервер:       while (frontend.readClean(buf)) server.sendAudio(buf, n)
  ответ → динамик:       while (server.readAudio(buf)) audioOut.write(buf, n)
  команды → сценарий:    while (server.pollCommand(c)) session.onServerCommand(c)
  состояние:             session.onConnection(...), session.onPlaybackIdle() при окончании
  действия → модули:     while (session.pollAction(a)) switch (a) { … вызовы модулей … }
```

`switch` по действиям — это маршрутизация, не логика: каждое действие —
один вызов одного модуля.

## 7. Протокол WebSocket

- ESP — клиент. Адрес: `ws://<SERVER_HOST>:<SERVER_PORT>/device`.
  `SERVER_HOST`, `SERVER_PORT`, `WIFI_SSID`, `WIFI_PASSWORD` — в `secrets.h`.
- **Бинарные сообщения** — звук: PCM, 16 кГц, 16 бит со знаком,
  little-endian, моно. ESP шлёт кадрами по 512 отсчётов (1024 байта, 32 мс).
  Сервер — любыми кусками чётной длины.
- **Текстовые сообщения** — JSON с полем `type`.

**Ход (`turn`).** Каждый вопрос-ответ — один ход с номером. ESP увеличивает
номер при каждом `wake` (с 1 после старта). Номер есть во всех сообщениях
хода, и в ответах сервера тоже. Так ESP отличает ответ на текущий вопрос
от запоздавшего ответа на перебитый.

ESP → сервер:

| `type` | Поля | Когда |
|---|---|---|
| `hello` | `fw`, `sample_rate`: 16000, `format`: `"pcm_s16le"`, `channels`: 1 | Сразу после подключения |
| `wake` | `turn` | Слово услышано, дальше пойдёт звук вопроса этого хода |
| `utterance_end` | `turn`, `reason`: `vad` / `timeout` / `server` / `no_speech` | Звук вопроса закончился. При `no_speech` сервер не отвечает |
| `barge_in` | `turn` (перебитый) | Ход перебит словом; сервер прекращает ответ на него. Сразу следом идёт `wake` с новым `turn` |
| `playback_done` | `turn` | Ответ доигран до конца |

Сервер → ESP:

| `type` | Поля | Что делает ESP |
|---|---|---|
| `stop_listening` | `turn` | Сервер сам понял конец фразы → как `SpeechEnd` |
| `reply_start` | `turn` | Дальше пойдёт звук ответа этого хода |
| `reply_end` | `turn` | Звук ответа закончился; когда доиграет — `playback_done` |
| `stop_playback` | — | Оборвать текущий ответ |
| `volume` | `value`: 0..1 | Громкость |
| `tone` | `name`: `wake` / `error` / `thinking` | Проиграть встроенный звук |

Правила для ESP:
- Сообщения с `turn`, не равным текущему, игнорируются.
- Бинарный звук принимается только между `reply_start` и `reply_end`
  текущего хода, остальной отбрасывается.
- `reply_start` текущего хода в `Listening` (сервер ответил раньше, чем ESP
  заметила конец фразы) → ESP прекращает передачу звука, шлёт
  `utterance_end{reason:"server"}` и начинает воспроизведение.

Правило для сервера: звук ответа слать не быстрее чем ~на 10 с впереди
воспроизведения (очередь ESP — 30 с).

## 8. Задержка

Цель — ~1–2 с от конца фразы до начала ответа при потоковом сервере.
Со стороны прошивки:
- конец фразы: 500 мс тишины (настройка), плюс `stop_listening` от сервера;
- Wi-Fi без энергосбережения;
- звук уходит кадрами по 32 мс сразу, без накопления;
- ответ начинает играть после ~100 мс в очереди.

## 9. Тестовый сервер

`tools/test_server/` — простой сервер на Python (библиотека `websockets`)
для проверки прошивки без нейросети:
- режим «эхо»: принимает вопрос, после `utterance_end` отправляет его же
  обратно как ответ (`reply_start` → звук → `reply_end`);
- консоль: отправить `volume`, `tone`, `stop_playback`, `stop_listening`;
- печатает все сообщения от ESP.

Arduino IDE папку `tools/` не компилирует. `docs/`, `tools/` и
`src/common/` добавлены в «Структуру» `CLAUDE.md` вместе с этим документом.

## 10. Порядок работы (каждый пункт — отдельный PR)

1. **Каркас.** `SmartEsp.ino` (пустая связка), `src/common/Types.h`,
   `README.md` (настройки IDE, ядро, библиотеки с версиями),
   `secrets.example.h`. Проверка: собирается и стартует.
2. **`audio_out` + `audio_in`.** Проверка: сигнал на динамике, уровень
   микрофона в Serial.
3. **`voice_frontend`.** Проверка: «Hi, ESP» в тишине и во время звука из
   `audio_out` — как в пробной прошивке. После мёржа ветка
   `spike/wakeword-aec` удаляется.
4. **`wifi_link`.** Проверка: подключение, переподключение после
   перезапуска роутера.
5. **`server_link` + тестовый сервер.** Проверка: `hello` доходит, команды
   с консоли сервера доходят до ESP.
6. **`session` + полная связка.** Проверка: полный сценарий с эхо-сервером,
   включая перебивание.

## 11. Решения, принятые без обсуждения (проверить)

- Таймауты `Listening`: 5 с без речи → отмена; 10 с от слова → отправка
  того, что есть (раздел 5).
- Номер хода `turn` в протоколе и правила игнорирования (раздел 7).
- Очередь ответа 30 с, сервер не опережает больше чем на ~10 с (6.1, 7).
- Модуль `session` для логики сценария (6.6).
